# 0. Центральная модель OSTEP: три независимые, но связанные проблемы

Операционная система создаёт удобные и защищённые абстракции поверх конечных физических ресурсов:

1. **Virtualization / Виртуализация:** процесс видит собственный CPU-контекст и адресное пространство, хотя физическое процессорное время и RAM разделяются. Главные механизмы — прерывания, trap/system call, контекстные переключения, планировщик, страницы, MMU, TLB, swap.
2. **Concurrency / Конкурентное выполнение:** несколько потоков исполняются в неопределённом порядке и способны взаимодействовать через общую память/ресурсы. Главные проблемы — гонки, атомарность, взаимное исключение, ожидание, starvation, deadlock, условные переменные и очереди.
3. **Persistence / Долговременное хранение:** результат, созданный в RAM, должен пережить сбой процесса, ОС и питания, если это обещано приложением. Требуются понимание устройств, API файлов, файловых систем, порядка операций записи, journal/WAL, проверок целостности и восстановления.

**Дополнительно в доступной авторской редакции:** распределённые системы и безопасность, где локальные гарантии осложняются сбоями сети/узлов, доверительными границами и контролем доступа.

**Сквозное различие:** *mechanism* описывает **как** выполнить операцию; *policy* — **какую** операцию выбрать/какой ресурс выделить. Конкретная политика планирования или вытеснения страницы может смениться без переписывания фундаментального механизма.

Это фундаментальные свойства ОС, а не утверждение о том, что отдельное приложение обязано самостоятельно реализовывать scheduler, файловую систему или виртуальную память.

# I. Виртуализация CPU: процессы, прямое исполнение, планирование

## Глава 4. Абстракция процесса

**Процесс ≠ программа.** Программа — пассивный набор инструкций/данных; процесс — выполняемый экземпляр с состоянием: адресное пространство, регистры, program counter, stack pointer, открытые дескрипторы, состояние исполнения.

**Time sharing** позволяет ограниченному числу физических CPU создавать иллюзию множества исполняемых процессов. **Space sharing** разделяет ёмкость, например блоки диска. CPU time sharing несёт цену — переключения, cache locality, очереди, непредсказуемая задержка.

**Состояния:** running, ready, blocked/waiting, с переходами из-за вытеснения и I/O. «Программа не загружает CPU» не означает «ничего не ожидает».

**Практический вывод:** длинная задержка API может быть ожиданием сети, файлового дескриптора, БД, блокировки или планировщика, а не недостаточной мощностью CPU.

## Глава 5. Process API: fork, exec, wait

UNIX разделяет:
- \`fork()\` — создать дочерний процесс с собственным адресным пространством и идентификатором, наследуемой средой/ресурсами согласно правилам;
- \`exec()\` — заменить выполняемый образ новой программой внутри процесса;
- \`wait()\`/семейство — дождаться или учесть результат дочернего процесса.

**Ключевое свойство:** относительный порядок исполнения родителя и потомка после fork не фиксирован; нельзя делать основанную на порядке print() бизнес-логику. Разделение fork/exec исторически используется shell, пайпами и управлением потоками процессов.

**Серверный перенос:** если процесс перезапущен, его локальные переменные не сохраняют смыслового статуса подтверждённой операции; нужна внешняя проверяемая долговременная истина.

## Глава 6. Limited Direct Execution

Чтобы сохранять производительность, пользовательский код часто исполняется **непосредственно** на CPU, но под контролем ОС. Защита строится через privileged/user mode, trap to kernel, interrupt/timer, ограниченные операции, управление контекстом.

Разделять две задачи:
- **restricted operations:** процесс не вправе произвольно управлять оборудованием/памятью;
- **regaining control:** ОС должна получить контроль при системном вызове, исключении или прерывании, иначе программа могла бы удерживать CPU бесконечно.

**Перенос:** service process не равен привилегированному администратору сервера; операции модернизации ОС и ядра требуют отдельной оценки безопасности.

## Главы 7–10. CPU scheduling

**Базовые показатели:**
- Turnaround = время завершения − время прихода.
- Response = время первого запуска/ответа − время прихода.
- Waiting = суммарное время в ready queue.
- Throughput = завершённая работа за единицу времени.
- Fairness/priority и стоимость переключения могут конкурировать.

**FIFO/FCFS** прост, но подвержен «эффекту конвоя». **SJF/STCF** сокращают среднее ожидание/turnaround в идеализированной модели при известных/оцениваемых временах задач, но могут вредить fairness и не всегда применимы в настоящей ОС.

**Round Robin** даёт отзывчивость интерактивным задачам, но маленький квант увеличивает overhead переключений. Нет квантa, оптимального для всех workloads.

**Multi-Level Feedback Queue (MLFQ):** меняет приоритеты на основе наблюдаемого поведения, стараясь обслуживать интерактивные и CPU-bound задачи; требует защиты от голодания и механизма периодического восстановления приоритетов.

**Lottery scheduling:** tickets определяют вероятностную долю ресурсов, а не гарантированное точное время в каждом коротком промежутке; полезный пример разделения политики и механизма.

**Multi-CPU scheduling:** локальные очереди, cache affinity, load balancing и миграция задач могут конфликтовать. Количество CPU ядер само по себе не даёт пропорционального ускорения одного последовательного запроса.

**Применение за пределами ОС:** планировать серверную очередь задач по SLO, стоимости и последствиям starvation; **это аналогия**, не разрешение вручную переопределять scheduler ОС.

# II. Виртуализация памяти

## Глава 13. Address Spaces

Каждый процесс видит **собственное виртуальное адресное пространство**. Код, статические данные, heap и stack могут иметь похожие логические адреса в разных процессах, но ссылаться на разную физическую память.

**Ключевые свойства:** transparency (удобная иллюзия), efficiency (низкая цена трансляции) и protection/isolation (память чужого процесса недоступна без соответствующего механизма).

**Практика:** нельзя оценивать память сервера только по сумме одинаковых виртуальных адресных пространств; нужно учитывать shared pages, resident memory, cache, swap и поведение конкретной ОС.

## Главы 14–17. API памяти, трансляция, сегментация, свободное место

В C \`malloc\`/ \`free\` — абстракции пользовательского аллокатора, а \`mmap\`, \`brk\` и другие механизмы относятся к системе управления памятью. Ошибки указателей, двойное освобождение, use-after-free и утечки создают повреждения или рост RSS.

**Address translation:** аппаратный MMU преобразует virtual→physical с проверками прав; исходные base/bounds и segmentation — исторические/концептуальные модели с разными ограничениями. **Free-space management** включает стратегии разделения блоков, fragmentation, coalescing, free lists.

**Управленческий перенос:** большое число мелких выделений памяти/структур может создавать overhead и фрагментацию, но перед оптимизацией нужен инструмент и реальные измерения.

## Главы 18–20. Paging, TLB, таблицы страниц

**Paging:** пространство памяти разбивается на страницы, сопоставляемые физическим frames; уменьшает некоторые типы внешней фрагментации, но требует таблиц трансляции и создаёт свои затраты.

**TLB** — быстрый кэш трансляций в процессоре. TLB misses заставляют делать более дорогой page walk, поэтому locality и размер рабочего набора данных влияют на производительность.

**Многоуровневые таблицы страниц** сокращают хранение таблиц в неиспользуемых диапазонах адресного пространства. Латентность обращения определяется не только алгоритмом приложения, но и расположением данных в памяти/кэшах.

**Нюанс:** попадание в page cache ОС для данных с диска не тождественно попаданию в CPU cache или TLB — это разные уровни и подсистемы.

## Главы 21–23. Swap / beyond physical memory

RAM ограничена. При нехватке физической памяти ОС может **вытеснять/перечитывать** страницы через storage, что на порядки медленнее доступа к RAM и может приводить к thrashing.

**Page fault ≠ всегда авария.** Некоторые faults — нормальная часть ленивой загрузки и copy-on-write; другие — дорогие обращения к диску; третьи — нарушения прав/адресов.

**Page replacement** (FIFO, LRU-like, clock и др.) стремится выбрать страницы для замещения исходя из локальности и доступного состояния. Лучший алгоритм зависит от нагрузки, измерений и стоимости ведения метаданных.

**Практика:** при долгом p99 измерять resident set, page faults, swap activity, OOM kills и конкурирующие процессы; простое «выделить больше RAM» без диагноза может не исправить блокировки.

# III. Concurrency: потоки, взаимное исключение, сигнализация, ошибки

## Главы 26–27. Threads и Thread API

Потоки внутри процесса разделяют адресное пространство/heap и часть ресурсов, но имеют отдельные регистры/stack/состояние исполнения. Это облегчает совместную работу, но создаёт **непредсказуемые interleavings**.

**Race condition:** результат зависит от порядка действий потоков. Даже \`counter++\` в реальной машине может включать отдельные read, modify, write; одновременные инкременты способны потеряться.

**Critical section:** часть логики, где необходимо исключительное/атомарное взаимодействие с общим состоянием.

**Нельзя считать:** asyncio/event loop автоматически исключает бизнес-гонки, особенно если запросы исполняются в разных процессах или в ходе yield/await пересекаются с другой операцией.

## Главы 28–29. Locks, mutex, конкурентные структуры

Mutex обеспечивает взаимное исключение, но хорошая синхронизация оценивается по **correctness, fairness, performance**. Реализация с spinlock может расходовать CPU во время ожидания; при конкуренции и на одном CPU особенно невыгодна.

**Принципы:**
- блокировать минимально необходимый критический участок;
- явно формулировать инвариант, защищаемый замком;
- согласовать порядок приобретения нескольких locks;
- избегать I/O и длительных операций под lock без обоснования;
- не заменять БД-транзакцию локальным mutex, если запись исполняется в нескольких процессах/машинах.

**Concurrent data structures** — увеличение throughput может требовать разбивки по locks/шардам, но сложность растёт; начинать с простой правильно синхронизированной структуры, улучшать лишь по измерению.

## Главы 30–31. Condition Variables, Semaphores

**Condition variable** связывает ожидание некоторого *предиката* с mutex. Стандартный паттерн: под lock проверять условие в \`while\`, при отсутствии ожидать, после пробуждения снова проверить. Почему цикл? Возможны spurious wakeups и изменение условия другим потоком до возобновления.

**Semaphore** управляет разрешениями/числом доступных ресурсов с \`wait\` и \`post\`; бинарный семафор может выполнять задачу mutex, счётный — ограничивать количество одновременных операций.

**Producer–consumer:** очередь + синхронизация «есть работа» и «есть место» защищают от потерянной работы/перезаписи. Корректная сигнализация, условие и объём очереди важнее простого увеличения числа worker processes.

**Иллюстрация для веб-системы:** очередь обработки событий, семафор ограничения одновременного доступа к внешнему API. Сам по себе семафор не заменяет долговременную очередь и idempotent event processing.

## Глава 32. Common Concurrency Problems

Авторы подробно различают:
- **non-deadlock bugs:** нарушение атомарности и неправильный порядок событий;
- **deadlock:** взаимное ожидание ресурсов.

**Четыре условия deadlock:** mutual exclusion, hold-and-wait, no preemption, circular wait. Исключение хотя бы одного условия разрушает соответствующую классическую структуру deadlock.

**Практическое правило:** глобально договориться о порядке приобретения locks, уменьшить число пересечений, проверять liveness, тестировать конкурентные повторы/таймауты и определять область отказа.

**Слабость обычного теста:** гонки зависят от редких расписаний и могут не воспроизводиться при локальном последовательном запуске. Нужны стресс/инъекция отказа на **безопасном тестовом экземпляре**.

## Глава 33. Event-Based Concurrency

Event loop получает события и исполняет handlers. Используются readiness механизмы \`select\`, \`poll\` и их современные аналоги. Преимущество — контролируемая организация многих I/O работ; опасность — блокирующий обработчик может задерживать **все** события этого цикла.

**Неблокирующий I/O** ≠ бесконечная пропускная способность. Длинный CPU-bound callback, синхронная файловая запись, lock или тяжёлое кодирование ответа блокируют event loop независимо от того, насколько современный framework.

**Для Python:** это объясняет часть ограничений asyncio, но подробная семантика Python, GIL и библиотеки — в самостоятельном источнике, а не в OSTEP.

# IV. Persistence: устройства и файловые системы

## Главы 36–38. I/O, HDD, RAID

**I/O path** содержит системные вызовы, device driver/controller, interrupts/DMA и очереди устройств. Физическая задержка складывается из подготовки запроса, ожидания, работы контроллера и передачи данных.

**HDD:** seek + rotation + transfer; последовательные большие обращения существенно отличаются от множества мелких случайных операций.

**RAID:** redundancy/throughput trade-offs, стоимость записи parity, отличие полосы от надёжности. **RAID не является backup**: логическое удаление и ошибка приложения воспроизводятся на всех зеркалах/репликах.

## Главы 39–40. Files, Directories, File-System Implementation

**File** — последовательность байтов с именем, metadata и файловым дескриптором при открытии. Директория связывает имена и inode/объекты. \`open\`, \`read\`, \`write\`, \`close\`, \`lseek\`, \`stat\`, \`rename\`, \`link\` имеют разные гарантии, разные модели ошибок и системных затрат.

**Ключевая разница:** успешный \`write()\` обычно означает передачу в подсистему ОС, а не всегда физически устойчивую запись. Для требуемой durability используется \`fsync()\`/семейство и соответствующие гарантии конкретной ФС/устройства. Для новой записи имени после \`rename\` иногда требуется также синхронизация директории. Это зависит от ОС, ФС, оборудования, mount options и реализации — не обещать универсальную устойчивость, просто вызвав API.

**File system internals:** inode, block/inode bitmaps, directories, direct/indirect pointers, metadata, free space. Малое изменение файла может требовать нескольких раздельных обновлений метаданных.

## Глава 41. Fast File System (FFS)

Группировка связанных inode/data, локальность размещения и геометрия устройств могут сокращать seek cost. FFS иллюстрирует, что результат ФС определяется не только семантикой API, но и **физическим размещением**.

**Уточнение:** многие исторические оптимизации HDD плохо переносятся дословно на SSD/NVMe; концепт locality остаётся, конкретные устройства отличаются.

## Глава 42. Crash Consistency: fsck and Journaling

**Главный предмет:** системный сбой между несколькими независимыми записями может оставить файловую систему в частично обновлённом состоянии.

**Подходы:**
- \`fsck\` восстанавливает согласованность структуры после сбоя, но сканирование дорого на большом хранилище.
- **write-ahead logging (WAL)/journaling:** заранее записать информацию о будущем изменении, затем checkpoint/replay/очистка после устойчивого commit в нужном порядке.
- **data journaling** записывает и данные, и metadata, но может повышать write amplification;
- **metadata journaling** уменьшает объём журнала и требует правильного порядка передачи user data, иначе возможна утечка старых или неполных данных;
- write barriers/flush ordering особенно существенны из-за кэшей и возможного переупорядочивания.

**Очень важное различие:** журналирование **ФС** не равно транзакционному журналу приложения или базы данных. ФС может восстановить целостность своих блоков, но не обеспечить, что бизнес-операция «сохранить ответ + начислить награду» атомарно выполнилась на уровне приложения. Нужна БД-транзакция, идемпотентность и независимое восстановление.

## Глава 43. Log-Structured File Systems

**LFS** превращает множество небольших модификаций в последовательную запись больших сегментов. Отличия: буферизация, checkpoint, segment cleaning, выбор живых данных, write amplification и сложность восстановления.

**Риск:** удобная оптимизация последовательных записей требует дополнительной работы по сборке мусора/очистке сегментов. Принцип не означает, что все log-structured системы всегда быстрее.

## Глава 44. Flash-based SSDs

**Flash** имеет страницы и стираемые блоки, требует flash translation layer (FTL), wear leveling, garbage collection, иногда overprovisioning; долговременная latency может возрастать при записи/GC.

**Применение:** p99 дисковых операций зависит от внутренней работы устройства; отсутствие движущихся частей не отменяет неожиданных задержек или ошибок целостности.

## Глава 45. Data Integrity and Protection

**Ошибки хранения** возможны без полного отказа диска: битовые повреждения, неправильный блок, «тихая» коррупция. **Checksums** позволяют обнаружить часть несоответствий, но любые конечные хеши/контрольные суммы имеют вероятность коллизий; необходима модель угроз.

**Сочетать:** checksum + redundance + backup + возможность фактического восстановления. CRC не равно криптографическому MAC; хеш целостности без доверенного места хранения не даёт аутентичности.

**Нельзя:** считать резервную копию здоровой только потому, что её файл существует. Проверка восстановления должна быть независимой.

# V. Distributed Systems и дополнения о безопасности

## Главы 47–51. Distributed Systems, NFS, AFS

**Распределённая система** объединяет несколько узлов, но с новыми типами ошибок: сеть может задержать/потерять/дублировать ответ, один узел продолжит работать после сбоя другого, клиент не всегда знает, произошло ли действие до таймаута.

**RPC не становится локальным вызовом** только от схожего синтаксиса. За ним существуют сериализация, сеть, retries, timeout и частичный отказ.

**NFS** показывает trade-offs stateless серверов и семантики кэша; **AFS** — иной выбор клиентского кэширования и consistency. Нельзя механически переносить гарантии локальной POSIX-ФС на NFS или распределённое object store.

**Exactly-once:** без надёжной идентичности операции и поддерживаемого журналом/протоколом состояния повтор может применить действие несколько раз. Ответ с timeout не определяет, был ли commit, пока это не проверено.

**Практическое правило:** задавать idempotency key, хранить долговременный итог логической операции, различать «не подтверждено клиенту» и «не выполнено сервером» и проектировать повторы как нормальную часть сетевого приложения.

## Дополнительные главы 53–57. Security: Peter Reiher

**Атрибуция:** на сайте оригинала главы этого блока подписаны **Peter Reiher (UCLA)** — корректно указывать отдельного автора.

**Темы:** постановка угроз и безопасности, authentication, access control, cryptography, безопасность распределённого взаимодействия.

**Универсальные различия:**
- **Authentication:** удостовериться, кто предъявляет запрос.
- **Authorization/access control:** удостовериться, что данному участнику **разрешено** действие.
- **Confidentiality:** защитить содержимое от чтения.
- **Integrity/authenticity:** обнаружить неправомерную модификацию или подделку.
- **Availability:** обеспечить доступность несмотря на предусмотренные отказы и атаки.

**Критические ошибки:** считать Telegram-id/параметр из тела запроса подтверждением личности без серверной проверки; использовать обычный checksum вместо криптографической проверки подписи; доверять лишь внешнему UI скрытой кнопки; хранить private token в клиентском JS.

**Граница:** эти главы не освобождают от актуальных security standards, threat modeling, независимой инженерной проверки криптографических протоколов и действующих законодательных требований.

# VI. Двенадцать фундаментальных различений, которые нельзя терять

| Пара | Значение для проекта |
|---|---|
| Процесс vs программа | Runtime имеет состояние, бинарник — нет |
| Поток vs процесс | Потоки делят память, процессы имеют более сильные границы |
| Running vs Ready vs Waiting | Не всё ожидание означает загрузку CPU |
| Mechanism vs Policy | Реализация механизма отдельно от выбора поведения |
| Virtual memory vs Physical memory | Виртуальный размер не равен занятому RAM |
| Page cache vs CPU cache vs TLB | Разные ресурсы и разные виды misses |
| Race vs Deadlock | Неверный результат/порядок против бесконечного взаимного ожидания |
| Lock vs Transaction | Взаимное исключение не гарантирует durability и атомарность нескольких DB изменений |
| write vs fsync | Принятая запись ≠ подтверждённая устойчивость на устройстве |
| FS journaling vs DB WAL | Гарантии ФС ≠ атомарный игровой результат |
| RAID vs Backup | Redundancy не возвращает ошибочно удалённые данные |
| RPC timeout vs operation failure | При timeout сервер мог уже завершить действие |

# VII. Универсальная диагностическая карта

## Если «сервер иногда зависает»

1. Разделить ошибки на **CPU execute, ready/scheduler wait, mutex/semaphore/queue wait, memory/page fault, filesystem/disk wait, network wait, remote server wait**.
2. Уточнить p50/p95/p99 и размер выборки; различать клиентскую и серверную сторону.
3. Посмотреть конкурирующие задачи и состояние RAM/swap/FD.
4. Проверить, не блокируется ли event loop.
5. Если есть допустимые трассы — найти первый участок реального ожидания, а не выбирать виновника по общему % CPU.
6. Отдельно измерить correctness и доказанное время commit.
7. Только затем планировать конкретную оптимизацию на тестовом экземпляре.

## Если «иногда теряется прогресс»

1. Выделить момент **логического принятия решения**.
2. Разделить client acknowledgment и durable server record.
3. Проверить атомарность всех изменений в транзакции.
4. Проверить idempotency при повторах из-за timeout/двойного нажатия.
5. Проверить семантику файловой системы, БД и режим её журнала.
6. Проверить backup/restore независимым безопасным способом.
7. Не путать наличие файловой копии с доказательством восстановления.
8. Проверить оповещение об ошибке vs ложное «сохранено».

## Если «после увеличения числа workers стало хуже»

1. Различить число CPU cores, число потоков и доступные блокирующие ресурсы.
2. Проверить queue length, contention, DB write serialization и overhead переключения.
3. Проверить, не стало ли больше конкурирующих операций с одинаковой идентичностью.
4. Оценить fairness и starvation.
5. Не увеличивать параллелизм без способа корректно сериализовать критические DB инварианты.

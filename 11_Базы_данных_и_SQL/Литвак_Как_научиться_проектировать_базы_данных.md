# I. Метод книги — от предметной области к таблицам

## 1. Прежде чем открывать СУБД: изучить реальную задачу
**Авторская идея:** база данных — модель ограниченной части реальности, которую автор называет «предметной областью». Модель сознательно упрощает мир: в ней должны оставаться факты и связи, необходимые для задач программы.

Пример книги — поликлиника: врачи, пациенты, подразделения, посещения. Разработка начинается с анализа процессов, а не с перечня столбцов.

**Рабочий алгоритм анализа:**
1. Перечислить реальные процессы.
2. Установить, какие участники и объекты влияют на процессы.
3. Выявить документы, события и информацию, которую требуется помнить.
4. Понять вопросы, на которые будущая БД должна отвечать.
5. Отметить, что может изменяться и что должно сохраняться исторически.
6. Только затем проектировать таблицы.

**Ограничение:** книга показывает концептуальную структуру, но производственная модель должна учитывать объём данных, операции чтения/записи, требования доступности, резервное копирование и восстановление.

## 2. Сущности и их атрибуты
**Сущность** — описываемый класс предметных объектов, **экземпляр** — отдельный представитель, **атрибут** — характеристика экземпляра.

Автор предлагает простой эвристический тест: существуют ли многие экземпляры с общими свойствами? Так в медицинской системе различаются сущности «Врач», «Пациент» и «Подразделение»; регистратура может рассматриваться как экземпляр подразделения.

**Не превращать эвристику в закон:** таблицы-справочники, единственный конфигурационный объект и другие одиночные сущности допустимы. Наличие нескольких экземпляров — полезная проверка, но **не математическое требование** существования сущности.

### Проверка атрибутов
- Принадлежит ли поле самой сущности?
- Может ли значение отсутствовать?
- Должно ли значение быть уникальным?
- Меняется ли оно со временем?
- Существует ли уже достоверный источник этого значения?
- Не храним ли один и тот же факт в нескольких местах с риском рассинхронизации?

## 3. Связи между сущностями
Автор рассматривает три базовых типа кардинальности:
- **1:1** — одному экземпляру с каждой стороны соответствует не более одного экземпляра другой.
- **1:N** — одному объекту соответствует множество объектов другого вида.
- **M:N** — возможно множество соответствий в обе стороны.

### Эвристика предложения с глаголом
Книга советует описывать связь обычным языком: «одно подразделение включает многих врачей», «один врач принимает многих пациентов» и наоборот. Два предложения с изменённым направлением помогают выяснить кардинальность.

**Сильная сторона:** позволяет объяснять структуру человеку без специальных знаний.

**Важное уточнение для работы:** формулировка «один/много» НЕ сообщает, допускается ли **ноль**. В промышленной ER-модели нужно отдельно задавать минимальную кардинальность (0 или 1), обязательность, уникальность, поведение при удалении/изменении и временные ограничения.

**Вторая оговорка:** отсутствие удачного глагола не доказывает отсутствия связи. Например, отношения могут быть косвенными, историческими, составными, зависящими от бизнес-процесса. Проверять на данных и реальных запросах.

## 4. ER-диаграммы
Книга проходит от наглядной нотации Чена к компактной нотации **Crow's Foot** («воронья лапка»).

Минимальные компоненты:
- сущности / таблицы;
- атрибуты / поля;
- первичные ключи (PK);
- внешние ключи (FK);
- кардинальность и обязательность связи;
- ассоциативные сущности для M:N.

**Рабочее правило:** схема должна помогать заметить дублирование и противоречия *до* написания кода.

# II. От сущностей к реляционным таблицам

## 5. Первичный ключ
Служит для однозначной идентификации строки и не может быть NULL; его значения уникальны.

### Естественный ключ
Состоит из реальных бизнес-атрибутов. Может быть из нескольких столбцов — составной ключ. Книга приводит примеры комбинаций, способных отличать запись.

### Суррогатный/искусственный ключ
Специальный идентификатор, например целое число или UUID. Удобен, если естественный ключ нестабилен, длинный или сложен для ссылок.

**Критическое дополнение:** добавление суррогатного PK **не отменяет** бизнес-ограничения уникальности. Если один участник может голосовать за один вариант только один раз, таблице голосов по-прежнему нужно явное ограничение на допустимое сочетание полей, даже если строка имеет свой уникальный ID.

### Для проекта викторины
Потенциальные сущности и ключи надо *проверить в реальной схеме*, а не создавать по предположению: пользователь; вопрос; ответ на вопрос; игровая сессия; рейтинг; начисление RP; вклад FP; факультет; голосование; событие; награда.

## 6. Связь 1:N
**Метод книги:** PK таблицы со стороны «один» становится **FK** в таблице со стороны «много». Например, у врача может храниться идентификатор подразделения.

Дополнительно в production необходимо решить:
- FK действительно существует в схеме, а не является лишь колонкой с названием `id`;
- может ли FK быть NULL;
- разрешено ли удалять родителя при существующих детях;
- нужны ли индексы по FK для конкретных запросов и операций;
- есть ли транзакция, которая поддерживает целостность при массовых действиях.

**Не смешивать** существование ограничения FK с существованием индекса: например, в PostgreSQL индекс по ссылающемуся FK автоматически не создаётся.

## 7. Связь M:N
**Метод книги:** создать отдельную ассоциативную таблицу с двумя внешними ключами. В медицинском примере факт посещения содержит идентификаторы врача и пациента и собственные атрибуты времени.

Появление M:N часто обнаруживает новую **сущность-событие**, ранее не замеченную в первоначальном анализе: запись об участии, посещении, назначении, голосовании и т.д.

### В игре
Например, связь «игрок участвует в задании» может требовать ассоциативную сущность:
- ID пользователя;
- ID задания;
- состояние участия;
- время начала и завершения;
- награда;
- версия правил;
- происхождение начисления.

**Нельзя полагаться на условие**, что «этот человек не сможет прийти дважды в один день». Реальные бизнес-процессы часто допускают повторения. Уникальные ограничения должны выражать *точное* правило приложения.

## 8. Связь 1:1, категоризация
Книга показывает модель общего объекта и разных его подтипов: общее оборудование и отдельные признаки компьютера/принтера. PK родительской таблицы используется также в подтипе; это один вариант физической модели наследования.

**Критическое дополнение:** фраза о том, что таблицы 1:1 «можно объединить», верна лишь в части случаев. Отдельные таблицы могут быть полезны из-за чувствительных данных, нагрузки, жизненного цикла, обязательности атрибутов или независимого владения данными. PK=FK в дочерней таблице — распространённая модель, но не единственная физическая реализация.

# III. Нормализация

## 9. Первая нормальная форма (1NF)
**Упрощённое объяснение книги:** не хранить в одном поле списки значений вместо отдельных отношений. Это помогает обращаться к данным по реляционной структуре без ненадёжного разбора строк.

**Проверка:** нет ли поля `participants`, содержащего строку с десятками ID через запятую; нет ли множества однотипных атрибутов `answer_1, answer_2, ...`, если количество динамическое.

**Уточнение:** строгая 1NF связана с устройством отношений и атомарностью в выбранной реляционной модели; JSON/массивы могут быть обоснованными типами современных СУБД. Утверждение «все списки запрещены» — полезная учебная эвристика, но не абсолютное производственное правило.

## 10. Вторая нормальная форма (2NF)
Таблица должна соответствовать 1NF и не иметь частичной зависимости неключевого атрибута от части составного ключа.

Пример: если в таблице фактов посещения хранить «специальность врача», зависящую только от ID врача, она дублируется и может противоречить другим строкам.

**Метод:** перенести свойство туда, где находится сущность, от которой оно зависит.

**Тонкость:** один столбец PK позволяет избежать частичной зависимости **от частей такого PK**, но не заменяет анализа всех кандидатных ключей, бизнес-правил и сторонних зависимостей.

## 11. Третья нормальная форма (3NF)
**Основной смысл:** устранить транзитивную зависимость неключевых полей от ключа через другие неключевые поля. В таблице врачей не следует копировать телефон подразделения, если единственным источником истины является само подразделение.

**Смысл:** уменьшить риск аномалий вставки, изменения и удаления.

### Практическое правило
Один доменный факт — один авторитетный источник записи, если нет доказанной причины для денормализации.

### Что книга НЕ исследует глубоко
- функциональные зависимости в полной строгой формулировке;
- BCNF, 4NF и 5NF;
- намеренная денормализация ради read-heavy нагрузки;
- материализованные представления, агрегаты, партиционирование;
- оптимизация индексов и запросов.

Проектировать правильную схему и оптимизировать её запросы — связанные, но разные задачи.

# IV. Восьмишаговый авторский алгоритм — прикладной пересказ

1. Исследовать процессы, участников и документы предметной области.
2. Выделить классы сущностей, даже если пока не все.
3. Найти реальные отношения между сущностями.
4. Сформулировать каждую связь в обе стороны и определить кардинальность.
5. Перейти от сущностей к таблицам и выбрать первичные ключи.
6. Реализовать FK с учётом 1:N и 1:1; использовать правила для M:N.
7. Добавить и осмыслить ассоциативные сущности, составить ER-диаграмму.
8. Проверить первые три нормальные формы и скорректировать модель.

**Дополнение для production-систем** (отдельное от книги):
9. Уточнить обязательность, уникальность, каскады удаления, ограничения CHECK, состояния и временные инварианты.
10. Прописать транзакционные границы, нагрузки, частые запросы и индексы.
11. Проверить миграции, совместимость старой и новой версии, резервные копии и план отката.
12. Реализовать нагрузочные тесты и профилирование до изменения больших таблиц.

# V. Применение к проблемам backend «Мир Поттера | Викторина»
**Отдельная рабочая интерпретация, НЕ диагностика реального кода.**

## 12. Какие проблемы может выявить аудит модели данных

1. **Одинаковый факт записан в разных таблицах.** Пример — текущий RP, исторические начисления и суммарный рейтинг. Без чёткой стратегии синхронизации данные расходятся.
2. **Нет ограничений уникальности.** Повторный webhook, двойной клик или сетевой retry могут создать две одинаковые записи участия/награды.
3. **Некорректная M:N-связь.** События и факультеты могут получить несогласованные записи участников.
4. **Большая транзакция и конкурентные записи.** Даже при правильной нормализации множество одновременных операций может вызвать блокировки.
5. **Сложные JOIN на больших таблицах.** Для них нужны индексы и анализ плана выполнения — **сама по себе нормализация лаги не устраняет**.
6. **Рейтинг пересчитывается полностью при каждом открытии Mini App.** Возможна потребность в агрегировании/кеше, но сначала проверить действительную реализацию и запросы.
7. **Отсутствует реестр начислений.** Невозможно восстановить, почему сумма RP или FP поменялась.
8. **Необратимые удаления и миграции.** Без бэкапов исправление дефекта становится рискованным.

Все восемь пунктов — **возможные причины/риски**, ни одна не утверждается обнаруженной в текущем репозитории.

## 13. Гипотетическая модель RP/FP и сессий
**Это пример схемы для анализа — не требование внедрить новые таблицы.**

| Сущность | Назначение | Пример доменного инварианта |
|---|---|---|
| User | Telegram-идентичность | внешний Telegram ID не дублируется |
| GameSession | попытка игрока | сессия принадлежит одному игроку |
| AnswerAttempt | зафиксированный ответ | события с уникальным идентификатором не обрабатываются дважды |
| RPTransaction | изменение RP с причиной | один и тот же источник награды начисляется по одной политике идемпотентности |
| HouseMembership | факультет игрока | правила допускают определённое количество текущих факультетов |
| FPContribution | зачёт личного вклада | транзакция связана с определённым основанием RP и версией правила |
| HouseTaskVote | выбор задания | допустимое число голосов на игрока и тур зависит от правил |
| AchievementGrant | выданная награда | одна и та же единичная награда не выдаётся многократно |

**Контекст установленных правил игры:** 1 FP за каждые 10 зачётных RP; остаток 0–9 сохраняется. Архитектура должна быть способна сохранять остаток и избегать двойного пересчёта; точные таблицы, транзакции и модели необходимо согласовывать с существующей реализацией.

## 14. Инварианты, которые стоит проверить

- Единственная достоверная запись об ответе/результате.
- Идемпотентность повторного события от Telegram.
- Атомарность «результат сессии + начисление RP + обновление счёта».
- Атомарность «учёт зачётного RP + вычисление FP с переносом остатка».
- Правильное поведение после рестарта сервера посреди транзакции.
- Повторное открытие Mini App не вызывает лишних изменений игровых данных.
- Нет «потерянного обновления» при двух одновременных действиях одного игрока.
- Сохраняется возможность доказать происхождение наград и пересчитать баланс по журналу.
- Удаление/изменение вопроса не уничтожает историю завершённых игр без осознанного правила.

## 15. Как проверять, не ломая production
1. Получить схему в режиме чтения, без изменения базы.
2. Собрать перечень запросов и операций при открытии приложения, старте вопроса, ответе и завершении игры.
3. Построить ER-диаграмму фактических таблиц.
4. Отметить PK/FK, индексы и уникальные ограничения.
5. Сверить фактические инварианты с бизнес-правилами.
6. Сопоставить операции с метриками задержек и ошибками.
7. Только после измерений составить отдельную миграцию с резервной копией и планом отката.

**Не путать** «стало удобнее проектировать данные» и «сервер больше не лагает». Причина нестабильности определяется измерениями.

# VI. Методологическая оценка

**Сильные стороны:** объясняет сущность, атрибут, связь, PK, FK и нормализацию понятным языком; даёт законченный алгоритм, последовательный пример и две нотации ER-диаграмм.

**Ограничения и места для уточнения:**
1. Один экземпляр **не запрещает** сущность.
2. Связь 1:1 — не обязательно повод объединять таблицы.
3. «Между сущностями нет глагола» — недостаточное основание отвергнуть связь.
4. Суррогатный PK не заменяет уникальные бизнес-ограничения.
5. Композитное значение «врач + пациент + день» не гарантированно уникально без бизнес-правила.
6. 1NF и атомарность в разных реляционных системах сложнее запрета любых списков.
7. Тип FK сам по себе не доказывает его индексирование или адекватную производительность.
8. Методы нормализации не подменяют observability, SQL profiling, конкуренцию, пулы соединений и резервное копирование.

**Сфера применимости:** исходный дизайн схемы и аудит целостности данных. Для эксплуатационных сбоев нужно продолжать изучение специализированных книг по PostgreSQL, backend reliability и наблюдаемости.

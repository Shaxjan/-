## 0. Условия перед любой технической работой

**Нельзя объявлять проблему найденной только по жалобе «игра лагает».**

Неизвестны и должны быть подтверждены:
- фактический язык/фреймворк сервера;
- тип и версия базы (PostgreSQL только гипотеза);
- URL/маршруты API и способ Telegram webhook/polling;
- провайдер, лимиты и топология инфраструктуры;
- наличие worker/фоновых задач/очередей/Redis;
- текущая стратегия игровых сессий и начисления RP/FP;
- последовательность деплоя и миграций;
- пользователи, время и условия сбоев.

На этапе аудита **не менять код, не трогать реальную БД, не выполнять нагрузочный тест на production и не копировать секреты**. Начать с read-only анализа репозитория, конфигурации без токенов, имеющихся логов и метрик.

## 1. Приоритеты пользователей и системы

Пользователь судит об исправности игры по действиям:
1. Mini App открывается.
2. Авторизация проходит.
3. Вопрос появляется.
4. Нажатие на ответ не вызывает подвисания.
5. Ответ принимается ровно один раз.
6. Сессия и жизни сохраняются.
7. RP начисляется точно по правилам.
8. FP вычисляется из зачётного RP с переносом остатка.
9. Рейтинг и прогресс отражают действительные данные.
10. Отдельный отказ внешнего сервиса не уничтожает сохранённый прогресс.

Приложение может возвращать HTTP 200, но делать неверное начисление; такой результат всё равно **неуспешен**.

## 2. Карта зависимостей (нужно проверить)

```text
Пользователь / Telegram Mini App
    ├─ frontend: HTML, JS, CSS, network/cache, UI state
    ├─ Telegram initData → проверка подписи на backend
    └─ backend API
         ├─ route / middleware / auth
         ├─ игровая логика / сессия
         ├─ СУБД + connection pool
         ├─ начисления и история изменений
         ├─ рейтинги и факультеты
         ├─ фоновые очереди/планировщик (если есть)
         └─ Telegram Bot API / вебхуки
    Hosting / proxy / TLS / DNS / ресурсы / logging / backup
```

Всё после Mini App — проверяемые предположения до изучения кода.

## 3. Что измерять, чтобы перестать угадывать

### Пользовательские показатели
- Число запусков и процент успешно открывших приложение.
- Время от открытия до возможности ответить.
- Доля запросов ответа, завершившихся подтверждением.
- Число случаев дублированного или пропущенного начисления.
- Доля завершённых сессий, отдельно по режиму.
- Жалобы, привязанные к времени и версии.

### HTTP/API
- Requests per second (RPS).
- Распределения задержек: p50, p95, p99.
- Ошибки по endpoint и HTTP status.
- Timeout и cancelled request.
- Версия кода, дата деплоя.
- Корреляционный request_id.

### База
- Длительность и частота наиболее дорогих SQL.
- Количество активных, простаивающих и ожидающих соединений.
- Ожидание блокировок / deadlock / конфликт сериализации.
- Состояние диска, транзакций и обслуживания.
- Динамика размера таблиц/индексов.
- Нагрузочный профиль по времени суток.

### Система и хостинг
- CPU, RAM, OOM, throttling.
- Частота перезапусков.
- Диск и сетевые ограничения.
- Зависимости, DNS и TLS.
- Логи сервера и инфраструктуры.

**Важно:** для SLO задавать первоначальные цели после получения baseline, а не выдумывать внешне красивые проценты.

## 4. Дерево диагностики по симптомам

| Наблюдение | Прежде всего проверить | Возможная мера лишь после проверки |
|---|---|---|
| Mini App грузится медленно | frontend, загрузка ресурсов, auth, startup API | оптимизация bundle, кэширования или bootstrap |
| Отдельная кнопка надолго зависает | route, DB query, lock, внешние вызовы | исправить конкретный блокирующий участок |
| После обновления ломается | версия, миграция, конфиг, зависимость | безопасный rollback/compatibility fix |
| Пик трафика приводит к 5xx | ресурсы, pool, rate limit, DB, очереди | ограничить нагрузку, увеличить реальную узкую часть |
| RP повторяется | повторные запросы, webhook, идемпотентность | уникальный бизнес-ключ + атомарные обновления |
| FP расходится с RP | транзакционная логика, остаток 0–9, повтор начисления | тест инварианта и корректировка транзакций |
| Пропадает прогресс при рестарте | хранилище сессии, commit, reconnect | устойчивое сохранение состояния |
| Бот не отвечает | Telegram API, обработчик событий, очередь | надежная повторная обработка без дублей |
| Периодические перезапуски | OOM, fatal error, health probe | исправить причину и отрегулировать probes |
| Нет признаков ошибки, но игрок жалуется | browser logs, timestamp, request IDs, client UI | end-to-end телеметрия и воспроизведение |

Не переписывать инфраструктуру, пока отсутствуют измерения.

## 5. Целостность RP/FP и история игрового события

Правило FP: **1 FP за каждые 10 зачётных RP, остаток 0–9 сохраняется**. Значит, при каждом начислении нужно гарантировать согласованное изменение накоплений.

**Необходимые инварианты, не навязывающие конкретную схему таблиц:**
1. Один логический ответ имеет один уникальный идентификатор события.
2. Результат ответа невозможно обработать дважды с повторным начислением.
3. Обновление игры и начисление согласованы транзакционно.
4. Одновременные ответы одного игрока не перезаписывают состояние друг друга.
5. Сохраняется объяснимое происхождение RP/FP.
6. Ошибка в середине операции оставляет либо старое согласованное состояние, либо полностью новое.
7. После повторного запуска приложения сохранённый прогресс точно совпадает с серверными данными.

Для PostgreSQL могут понадобиться `UNIQUE`, `ON CONFLICT`, атомарный `UPDATE`, транзакции и подходящий уровень изоляции. Выбор зависит от фактического стека, а не только от названия инструмента.

## 6. План безопасного исследования

### Этап A — паспорт инфраструктуры
Собрать read-only инвентаризацию:
- runtime и версию;
- хостинг/регион;
- процессы сервера;
- DB engine и драйвер;
- способы запуска и рестарта;
- webhook и очереди;
- HTTP routes;
- схему хранения данных;
- фактические timeout и retry;
- способ релиза;
- сбор логов.

### Этап B — восстановление наблюдаемого инцидента
Выбрать один повторяемый симптом: «долгое открытие», «ошибка ответа», «двойные очки» и т. п. Сверить точную временную метку, запрос, версию сервера, реакцию клиента.

### Этап C — поиск причины
Только после сбора метрик решить, проблема в:
- неправильном алгоритме;
- медленном SQL;
- транзакциях/блокировках;
- нехватке ресурсов;
- задержках стороннего сервиса;
- неверной настройке конкурентной работы;
- изменениях при релизе;
- фронтенде или сети.

### Этап D — ограниченная правка
Одна локализованная правка → тесты → измерение до/после → выпуск с планом отката.

### Этап E — защита от повторения
Дополнить мониторинг, автоматические тесты, runbook и проверку резерва.

## 7. Минимальный набор тестов после аудита кода

- открытие Mini App с новым и существующим пользователем;
- запуск/завершение обычной игры;
- длинная сессия марафона;
- двойной клик на один ответ;
- два параллельных HTTP-запроса;
- один и тот же webhook дважды;
- перезапуск в момент сохранения;
- временная недоступность базы;
- превышение timeout Telegram;
- загрузка рейтинга при большой истории;
- откат неудачного релиза;
- полное восстановление тестовой базы из backup.

**Нагрузочные испытания только на разрешённом стенде**, а не на реальных игроках.

## 8. Способы восстановления и снижения риска

- Backup отдельно от основного хостинга/экземпляра.
- Проверенная процедура restore.
- RPO и RTO, соответствующие допустимой потере игровой истории.
- История версий и привязка к релизам.
- Автоматические smoke-tests перед объявлением релиза успешным.
- Явные таймауты и ограниченные ретраи внешних запросов.
- Дедупликация событий.
- Ограничение числа параллельных операций, если bottleneck это требует.
- Задокументированный порядок действий при аварии.

## 9. Какие решения пока не обоснованы

**Нет оснований автоматически:**
- переходить на Kubernetes;
- разделять монолит на микросервисы;
- менять СУБД;
- добавлять Redis или новый брокер;
- арендовать существенно более мощный сервер;
- переписывать весь backend на другой язык;
- пересчитывать все RP/FP;
- удалять старые игровые сессии.

Все эти действия могут быть полезны при конкретной доказанной проблеме и вредны при неправильном выборе.

## 10. Следующие источники для углубления

Главные пробелы четырёх книг:
- специализация на incident response / SRE / observability;
- практика профилирования runtime приложения и event loop;
- connection pooling и конкурентность в используемом backend-framework;
- актуальный PostgreSQL execution engine и MVCC (если БД действительно PostgreSQL);
- системное нагрузочное тестирование и тестирование отказов;
- end-to-end мониторинг Telegram Bot API и Mini App.

**Главный приоритет:** не увеличивать библиотеку бесконечно, а применить уже изученное к read-only аудиту реальной архитектуры и журналов. Исправления производить только по подтверждённой причине и отдельно согласованному плану.

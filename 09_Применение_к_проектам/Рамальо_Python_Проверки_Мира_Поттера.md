**Тип:** отдельное проектное приложение. **Основной источник:** [«Fluent Python», 2e — расширенное частичное досье по авторским примерам](../06_Технологии_и_производство/Рамальо_Fluent_Python_2e_Официальные_примеры_досье.md). **Важное ограничение:** полный текст книги не изучен; доступны официальное содержание, preview главы 1 и несколько проверенных авторских исходников, в т. ч. исправление race condition.

## 1. Что может быть полезно независимо от игры

Рамальо учит пользоваться естественными протоколами Python, подбирать представления данных и понимать concurrency: \`dict\`, dataclass, Unicode, decorators, asyncio, workers, context managers, descriptors, types.

Для продукта интеллектуальной викторины **нельзя предполагать**, что текущее серверное приложение вообще использует Python, asyncio или конкретную ORM, пока технология не проверена на основе реального проекта. Перечисленные проверки применять **только если соответствующий язык и механизм действительно существуют**.

## 2. Возможные зоны диагностики Python backend

| Тема | Что проверить read-only | Что считать доказательством | Чего нельзя делать |
|---|---|---|---|
| Mutable state | Локальные кэши/списки ответов на уровне module/global | code path с изменяемым shared object | Объявлять гонку без воспроизведения |
| Dataclass/DTO | Соответствие правил JSON, domain validation, server authority | реальные class/validators/test cases | Считать \`typing\` защитой данных |
| Unicode | NFC/словарь текстовых ключей, обработка русских строк | требуемая семантика канона/идентификаторов | Нормализовать signed Telegram payload |
| Decorators | Где измеряется latency и не раскрываются ли аргументы | конкретный instrumentation logger | Копировать debug decorator с печатью PII |
| Async | Не блокируется ли event loop файловым/сетевым sync I/O | профилирование и safe code review | Переписывать весь backend на asyncio |
| Process/worker | Как передаётся состояние после restart/между workers | реальная topology/service/unit | Использовать process-local lock как транзакцию |
| Queue lifecycle | Кто гарантирует выдачу результата незавершённой работы | code path с \`join\`/sentinel/ack и тестом | Считать \`queue.empty()\` завершением всех jobs |
| Descriptors | Есть ли сложная «магия» хранения состояния | явный domain invariant и тест | Менять ORM internals без понимания |
| Python upgrades | Есть ли версии и несовместимые изменения | lockfile, runtime, CI | Устанавливать новую версию на production без rollback |

## 3. Особенно полезный авторский случай с race condition

Официальный файл автора [19-concurrency/primes/README.md](https://github.com/fluentpython/example-code-2e/blob/master/19-concurrency/primes/README.md) описывает исправление ошибки ранней версии демонстрационного кода. Условие «входная очередь jobs стала пустой» было принято за условие «вся работа завершена», хотя worker-процессы ещё могли исполнять задания. В результате **не все результаты доходили до сборщика**.

**Универсальное проектное применение:** если в игре есть background worker проверки вопросов/сохранения/отправки уведомлений/начислений, нельзя отмечать весь workflow завершённым на основе одной лишь пустой входной очереди. Необходима долговременная и наблюдаемая семантика результата. Но наличие таких background workers **не подтверждено**, и мы не заявляем, что баг реально существует у нас.

## 4. Вопросы по канону и Unicode

В русскоязычной викторине одинаково выглядящие символы могут иметь разную Unicode-композицию. В официальном \`normeq.py\` Рамальо показывает \`unicodedata.normalize('NFC', ...)\` и \`casefold()\`.

**Почему важно:** сверка имён персонажей, пользовательских ответов и текстового поиска может требовать единой политики, но проверка **выбора варианта теста** часто производится по стабильному идентификатору ответа, а не по строке. Не вводить нормализацию всюду, где она не нужна.

**Особое условие:** canonical quotes и конкретные формы перевода требуют сохранения исходной орфографии; нельзя автоматически менять буквы в текстах канона в попытке получить «универсально равные» строки.

## 5. Инвариант начислений важнее языка

FP = 1 за каждые 10 зачётных RP, остаток 0–9 сохраняется. Обычная игра не вычитает FP.

Даже если код полностью написан на Python:
- \`@dataclass(frozen=True)\` не создаёт транзакционность базы;
- \`asyncio.Lock\` защищает лишь заданный event loop/процесс, не все серверы;
- GIL — не гарантия атомарного начисления логической награды;
- \`async def\` не делает автоматического commit;
- \`typing.Protocol\` не проверяет подлинность пришедшего HTTP запроса;
- retry после timeout может прийти после успешного серверного commit.

**Правильная проектная постановка:** серверная операция имеет однозначную идентичность, валидное исходное состояние, атомарное применение правил и проверенный долговременный итог, а клиент получает согласованное подтверждение.

## 6. Десять исследовательских гипотез H30

**H30-01.** Есть ли в существующем backend Python-код? Установить фактическую технологию до применения языковых рекомендаций.

**H30-02.** Могут ли изменяемые global structures влиять на независимость игровых сессий? Проверить только код/логи после разрешения.

**H30-03.** Нет ли синхронных блокирующих вызовов в async handlers? Оценить profile и очередь.

**H30-04.** Не основано ли завершение фоновой работы на \`queue.empty()\` вместо гарантированного завершения/commit? Проверить конкретный pipeline.

**H30-05.** Отсутствует ли server validation для внешних данных, несмотря на аннотации \`typing\`? Проверить boundary.

**H30-06.** Не логируют ли decorators пользовательские id и подписи initData? Проверить privacy/секреты без публичного экспорта.

**H30-07.** Контракты текстов/Unicode в ответах могут отличаться от подписей/идентификаторов. Проверить независимые правила.

**H30-08.** Может ли concurrency повторить начисление после timeout? Проверить idempotency в тестовом окружении.

**H30-09.** Не используется ли float для точных денежных/очковых величин, где нужны int/decimal? Проверить типы и правила.

**H30-10.** Есть ли проверяемый CI с doctest/unit/integration и race/failure тестами? Сначала изучить действующий workflow, потом предлагать изменения.

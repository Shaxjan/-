## 1. Пользовательская проблема важнее общего процента загрузки CPU

Вместо «сервер иногда тормозит» требуется обозначить конкретную транзакцию с измеримым дедлайном:
- открытие Telegram Mini App до интерактивного экрана;
- получение первого вопроса после нажатия начала игры;
- отправка ответа и подтверждённое одноразовое начисление RP/FP;
- переход на следующий вопрос;
- сохранение состояния марафона и жизней;
- поиск пары, доставка хода и фиксация результата дуэли;
- отображение голоса/вклада в факультетскую активность.

**Каждый процесс может состоять из цепочки** client/WebView → сеть → прокси → приложение → очередь/lock → БД → ответ → клиентский рендеринг.

Потерянный пакет, повторный запрос или долгое ожидание блокировки может создать хвост p99 при низком среднем времени. **Наличие такого дефекта в игре не установлено**.

## 2. Гипотетические точки задержки

| Участок | Что измерить в read-only диагностике | Возможные причины | Как не перепутать |
|---|---|---|---|
| Первый экран | p50/p95/p99 time-to-interactive, ошибки JS | тяжёлый frontend, авторизация, веб-ресурсы | клиентское время ≠ только backend |
| Список режимов | ответ endpoint, загрузка данных | лишние запросы/JSON | отделять HTTP и рендер |
| Первый вопрос | wait-to-question, серверный latency | DB lookup, блокировка, сеть | вероятность ошибки зависит от конкретного сценария |
| Подтверждение ответа | p95 round-trip и server commit | транзакция/очередь записи | UI animation ≠ server commit |
| RP→FP | атомарность и response_ms | повторные операции, конкуренция | логировать только итог после подтверждения |
| Марафон | latency корректировки жизни | блокировки состояния, повтор попытки | не подменять корректность счёта скоростью |
| Дуэль | matchmaking wait отдельно от action RTT | недостаток пары, сеть, server pool | время поиска пары не равно техническому «лаганию» |
| Факультеты | медленные запросы топов | сортировка/индексы/группировка | результат зависит от реальной схемы |
| Production состояние | CPU/RAM/disk/net/error/restarts | ресурсный лимит, очередь, I/O | общий CPU% не доказывает CPU bottleneck |

## 3. Методика диагностики в будущих отдельных ТЗ

1. **Уточнить симптом.** Что именно пользователь ждёт, как часто и с какого момента? Определить SLO/границу, размер выборки, единый часовой пояс.
2. **Собрать минимально нужные исторические сигналы.** Только при разрешении и без приватных токенов: error rate, p50/p95/p99, размер очереди, CPU/RAM/I/O/network, версии продукта.
3. **Нарисовать гипотезу критического пути.** Указать последовательные/параллельные стадии, где могут копиться ожидания.
4. **Сравнить быстрый и медленный случай.** Потребуется корректный корреляционный id и соответствие timestamps между компонентами.
5. **Отделить исполнение от ожидания.** Планировщик CPU, блокировка БД, ожидание сети, memory pressure, fsync, клиентское отображение.
6. **Найти доказанное условие.** Изменилось ли что-то в конкурирующей нагрузке, кодовой версии, объёме данных, запросе?
7. **Оценить безопасную альтернативу.** Ограничить объём данных, изменить query, кэш, очередь, размер payload или конфигурацию — всё как гипотезы.
8. **Только отдельное согласование внедрения.** Проверка на копии, ограниченная область изменения, срок отката, таймер backup, один контролируемый restart только если явно утверждён.
9. **Сверить эффект.** p95/p99, ошибка, корректность игровых начислений, стоимость CPU/RAM/диска, жалобы пользователей.
10. **Сохранить вывод.** Отдельный факт, альтернативные объяснения и измерение, не «поставили лучший сервер и стало быстрее».

**Не запускать KUtrace, патчи Linux-ядра или высокочастотный trace на Beget без специальной инженерной оценки и разрешения.** На большинстве малых приложений начать с безопасных уже имеющихся метрик и журналов.

## 4. Десять диагностических гипотез H24-01–H24-10

**H24-01:** p99 открытия Mini App существенно превышает медиану у конкретной группы устройств/браузеров; проверять разрезы, не делать вывод без данных.

**H24-02:** задержка первого ответа обусловлена фронтендом/инициализацией, а не API; сравнить timestamps этапов при допустимой телеметрии.

**H24-03:** длинный хвост ответов связан с последовательными запросами или очередью записи SQLite; проверить по реальным server tracing и схеме, а не по одной величине CPU%.

**H24-04:** двойной запрос после таймаута приводит к нарушению консистентности; проверять idempotency на копии, не вызывать сбои на production.

**H24-05:** p95 в марафоне растёт вместе с длиной истории вопросов; нужно проверить размер сериализации/запросов без утверждения о текущей реализации.

**H24-06:** поиск пары в дуэлях — естественное ожидание соперника, не backend lag; измерять отдельно matchmaking и server execution.

**H24-07:** рейтинговые запросы факультетов создают редкие задержки при повышенной конкуренции; оценить планы запросов и график событий.

**H24-08:** фоновые задания/таймер backup периодически совпадают с хвостами latency; только read-only сопоставить интервалы, не менять расписание.

**H24-09:** тяжёлое избыточное логирование влияет на p99; измерить саму наблюдаемость и не увеличивать частоту бесконтрольно.

**H24-10:** не нужно покупать ресурсы, если bottleneck находится вне CPU/RAM сервера; разложить пользовательский critical path перед решением.

**Все H24 — гипотезы**. Из них не следует, что соответствующие ошибки или процессы действительно существуют.

## Дополнение 14.10.2026: изученная глава 6 о сетевых RPC

В [досье Сайтса №024](../12_Надёжность_и_наблюдаемость/Сайтс_Software_Dynamics_Предварительное_досье.md) теперь разобрана непосредственно из официального sample PDF **глава 6 «Measuring Networks»**, а не только оглавление.

**Новый диагностический маршрут (только после технического допуска):** клиент инициировал ответ → отправил запрос → backend получил → начал работу после очереди → завершил критическую операцию → отправил подтверждение → WebView получил → пользователь увидел результат.

- Измерять отдельно full user-perceived latency, actual backend processing, queue wait, network contribution и отрисовку.
- Проверять RPC retries, время сериализации, зависимые запросы и скачки latency при packet loss.
- Не вычитать client/server timestamp без уверенности в точной синхронизации часов; нужны надёжные trace correlations.
- Сайтс в книге использует высокоточное бинарное логирование, но небольшой backend **не обязан копировать этот формат**; выбирается безопасный минимум событий без пользовательских секретов.
- Ключевое условие — выяснить реальный **критический путь**. Параллельные RPC нельзя механически суммировать как последовательные.

# OSTEP №029 — системные гарантии игры «Мир Поттера | Викторина»

**Тип:** отдельное проектное исследование, не часть содержания основного учебника. **Базовый универсальный конспект:** [Арпачи-Дюрсо, «Операционные системы. Три простых элемента»](../10_Backend_и_архитектура/Арпачи_Дюрсо_Операционные_системы_Три_простых_элемента.md).
**Источники:** официальные PDF-главы https://pages.cs.wisc.edu/~remzi/OSTEP/ .
**Статус:** инженерные **гипотезы** и read-only диагностический план, **не** результат фактического просмотра живого сервера или SQLite. Кода, БД, конфигураций, таймеров backup и работы Codex исследование не касалось. **Дата:** 14.10.2026.

## 1. Что OSTEP меняет в понимании backend

Для любого игрового сервиса важно разделять **пять уровней**:
1. Игрок нажал кнопку и передал запрос.
2. Runtime process/thread/event loop обработал его.
3. Сервер выполнил логическую бизнес-операцию и транзакционный commit.
4. Ответ дошёл до WebView, и пользователь увидел новое состояние.
5. Данные могут быть восстановлены после сбоя процесса/ОС/хранилища.

**Нельзя делать вывод, что шаг 4 гарантирует шаг 5**, пока неизвестны правила транзакции, хранения, durability, backup/restore. И наоборот, клиент мог не получить ответ, хотя шаг 3 уже произошёл. Отсюда необходимость server-authoritative состояния и устойчивой идентичности операции.

## 2. Приложение трёх опор ОС к продукту

| Из OSTEP | Гипотетическая проблема | Правильная будущая read-only проверка | Ограничение |
|---|---|---|---|
| Процессы/планировщик | Медленные ответы из-за contention | Рабочий процесс, очередь runnable, CPU ready vs blocked | Не обвинять CPU без измерений |
| Виртуальная память | p99 растёт при swap/page fault | RSS, page faults, swap, OOM и параллельные процессы | Не покупать RAM до диагностики |
| Threads/concurrency | Повторный ответ начисляет дважды | Реальная атомарность и idempotency, порядок транзакций | Не менять серверный ledger без допуска |
| Event loop | Блокирующий callback задерживает все запросы | Измерить blocking code path/время обработчика | Не менять framework по догадке |
| I/O/fsync/journaling | «Сохранено», но после crash запись отсутствует | Согласованные гарантии SQLite/filesystem/config | Не переключать journal mode на production |
| Проверка целостности | Backup повреждён | Независимый контроль и restore-тест на отдельной копии | Наличие файла ≠ restore |
| Distributed failures | Timeout привёл к повтору | Request/operation ID, commit record и повтор | Timeout ≠ отсутствие записи |
| Authentication/access control | Клиент предъявляет чужой идентификатор | Серверная проверка доверенного Telegram initData и прав | UI не является security boundary |

Это **список возможных путей ошибки**, не заявление о реальном нарушении проекта.

## 3. Серверные инварианты RP/FP

**Утверждённое правило:** 1 FP за 10 зачётных RP, остаток 0–9 переносится. Обычная игра не должна вычитать FP.

Для \`r∈{0..9}\` прежнего остатка и \`k≥0\` новых зачётных RP:
\`fp_delta = floor((r+k)/10)\`
\`r_next = (r+k) mod 10\`.

**Три различные проверки:**
- **Детерминированная арифметика:** при любой паре r,k выполнен инвариант.
- **Конкурентность:** две независимые попытки одновременно начислить награду не нарушают итоговую счётную целостность.
- **Durability:** после коммита и перезапуска подтверждённое начисление сохраняется или восстанавливается.

**Нельзя путать** mutex одного Python-процесса и transaction/unique-key на общем долговременном хранилище. При нескольких worker processes локальный lock не обеспечивает общую защиту.

**Idempotency:** один логический ответ должен иметь единственную согласованную идентичность. Повтор вызова после timeout должен получать прежний итог, а не запускать новое начисление — если по фактическим правилам действие однократное.

## 4. Марафон и гонки состояний

**Исторически согласованные правила:** 3 начальные жизни, ошибка отнимает жизнь и может вернуть вопрос позже, каждые 15 правильных +1 жизнь.

Вопросы для будущего аудита:
- Где одна транзакция обновляет состояние серии и списание/начисление жизни?
- Не допускаются ли одновременные ответы на один и тот же ожидаемый вопрос?
- Может ли late reply от старой вкладки изменить состояние новой игры?
- Как фиксируется завершение серии при crash/timeout?
- Можно ли сделать правильное восстановление с согласованным источником истины?

Любой алгоритм из OSTEP о locks/semaphores **не изменяет** утверждённых правил; его применимость зависит от текущей архитектуры, которой здесь не видели.

## 5. Storage, journaling, backup

**Из книги:** файловое write-ahead journaling обеспечивает определённый класс FS crash consistency. **Наше приложение:** полноценный инвариант игровой БД требует отдельного DB transactional design.

Проверка в безопасном режиме при отдельном одобрении:
1. Определить текущую базу и версию SQLite/другой СУБД, реальные режимы journal/WAL.
2. Узнать, какие data mutations объединены в транзакцию.
3. Выяснить, когда UI получает подтверждение относительно commit.
4. Проверить, как обрабатываются retry/conflict/busy errors.
5. Уточнить, что входит в snapshot/backup и какие связанные файлы участвуют в согласованной копии.
6. Провести только одобренный независимый restore, без вмешательства в текущий график резервного копирования и без restart производственной службы.
7. Отдельно проверить, что каноническая база вопросов и игровые балансы возвращаются в одном допустимом согласованном состоянии.

**Запрет:** не удалять/переключать WAL, не делать live VACUUM, не переименовывать файлы БД, не останавливать таймер backup и не проводить аварийное отключение в production ради эксперимента.

## 6. Десять проверяемых гипотез H29

**H29-01.** Достаточно ли server-authoritative commit подтверждений для игрового начисления? Read-only проследить фактический путь ответа.

**H29-02.** Не расходятся ли состояние памяти одного процесса и persistent-состояние при restart? Сверить архитектуру, не отключая службу.

**H29-03.** Возможен ли повтор начисления при timeout? Проверить idempotency schema на копии/тестовом стенде.

**H29-04.** Локальная синхронизация не может защищать между несколькими worker processes. Проверить количество workers и реальные правила разделяемого состояния, не менять их.

**H29-05.** Может ли event loop быть заблокирован синхронным I/O? Проверить через существующие измерения и безопасный code review с отдельным разрешением.

**H29-06.** Есть ли связь между хвостом p99 и swap/GC/DB lock wait? Сверить историю ресурса/задержек, не принимать корреляцию за диагноз.

**H29-07.** Отвечает ли файл backup реальной возможности восстановить транзакционные данные? Выполнить отдельную процедуру проверки после явного согласования.

**H29-08.** Защищает ли сервер запросы от подмены игрока и повторного применения состояния? Изучить trust boundary Telegram/auth, без публикации секретов.

**H29-09.** Могут ли ошибки восстановления марафона затрагивать состояние жизней и отложенных вопросов? Сверить инварианты с тестовым кейсом.

**H29-10.** Понимает ли пользователь разницу между «ожидается», «ответ принят» и «подтверждено» при проблемном соединении? Макет UX и качественный тест отдельно от кода.

Ни одна гипотеза не подтверждает дефект в настоящем backend.

## 7. Совместное применение с Карвином и Сайтсом

**Карвин №023:** SQL schema и constraints, \`NULL\`, составные отношения — **правильность модели данных**.

**Сайтс №024:** наблюдение конкретной последовательности CPU/memory/disk/network/lock — **где прошло время и почему**.

**OSTEP №029:** гарантии и ограничения самого исполнения/памяти/хранения — **что может происходить ниже уровня приложения**.

**Рамальо №030:** Python async/process/model — **какие языковые решения могли создать или предупредить проблемы**.

**Синтез:** не следует исправлять игровую экономику, увеличивая RAM, как и не следует лечить блокировку очереди переименованием столбца. Диагноз требует разделения уровней системы.

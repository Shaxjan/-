# Предварительный SQL-аудит «Мира Поттера | Викторина»: направления из Билла Карвина

**Связано с №023:** [предварительное досье «Антипаттерны SQL»](../11_Базы_данных_и_SQL/Карвин_Антипаттерны_SQL_Предварительное_досье.md). Полная книга в Яндекс Книгах **недоступна**, её чтение **не завершено**. Этот прикладной материал подготовлен по издательскому оглавлению, общим инженерным принципам и ранее согласованным правилам игры; не является экспертным аудитом уже работающей SQLite-БД.

**Статус:** аналитический план только для read-only аудита при отдельном разрешении. **Никакие действия по live-БД, миграции, перезапуску, таймерам бэкапа и Codex не разрешены этим документом.**

## 1. Основные допущения

Исторически проект обсуждал использование SQLite, режимы начисления RP/FP, дуэли и марафон. Актуальная схема БД, включённость внешних ключей, индексы, journaling, worker concurrency и конкретные правила начисления **здесь не проверялись**.

Инварианты:
- RP — результат игры, FP — личный вклад в факультет.
- 1 FP / каждые 10 **зачётных** RP; остаток 0–9 переносится.
- Обычная игра не должна вычитать FP.
- Марафон: 3 жизни на старте, ошибка −1 жизнь и возвращает вопрос позднее, +1 жизнь за 15 зачётных правильных. Дополнительные бонусы после 100 не объявлять активной механикой без проверки.
- Возврат HTTP и повтор Telegram-события не должны создавать два начисления одного и того же логического ответа, если по правилам он однократный.

## 2. Таблица потенциальных SQL-антипаттернов

| Область | Что проверить read-only | Что может произойти | Доказательство |
|---|---|---|---|
| CSV вместо связей | Как хранятся участники, режимы и теги вопросов | Потеря ссылочной целостности, сложный поиск | DDL + репрезентативные строки без приватных данных |
| Keyless Entry | PK, UNIQUE, FK, CHECK и реально активный enforcement | Дубликаты, «сироты», неполные ограничения | Дамп схемы, тестовые объяснения |
| EAV | Нет ли одной таблицы произвольных параметров для всех игровых правил | Типы и инварианты не контролируются | Назначение таблиц, типы, проверки |
| Polymorphic FK | Не ссылается ли одна колонка на разные виды parent без контроля | Некорректные связи | Примеры логических отношений |
| Metadata Tribbles | Нет ли отдельной таблицы на каждую неделю или факультет | Дорогие миграции и отчёты | Каталог таблиц, планы запросов |
| Floating point | Как хранятся RP/FP/денежные суммы | Ошибки округления | Реальные типы, код расчёта, тест |
| Phantom files | Как хранится большой медиа-контент | Недоступность или разрыв транзакции | Схема, правила резервного копирования |
| Index Shotgun | Нет ли индексов «на всё» и отсутствующих на реальных горячих запросах | Дорогие записи или медленное чтение | Read-only EXPLAIN QUERY PLAN |
| NULL | Соответствуют ли бизнес-семантике NOT NULL/default | Неверные фильтры и отчёты | DDL и тесты |
| GROUP BY | Корректно ли выбираются лидеры, рекорды и максимум по группе | Случайно выбранная «не та» запись | SQL-код и пример на тестовой БД |
| Random selection | Как выбираются случайные вопросы без повторов | Деградация на больших корпусах | Планы, количественная оценка |
| Spaghetti Query | Не смешаны ли выбор вопроса и начисления в неконтролируемом запросе | Сложная диагностика ошибки | Разбор транзакционного пути |
| SQL Injection | Параметризованы ли пользовательские значения и сортировка | Компрометация данных | Code review отдельно |
| See No Evil | Как обрабатываются сбои записи | «Успешный» UI при фактически потерянном прогрессе | Error reporting и инварианты |
| PK vanity | Не перенумеровываются ли id ради непрерывности | Разрушение ссылок и журнала | Код миграций, политика ключей |

**Это возможные риски, не подтверждённые дефекты игры.** Не исправлять то, чего ещё не проверили.

## 3. Предварительный план read-only диагностики

1. Зафиксировать согласованную точку обследования и не менять production.
2. Сверить текущую реализацию с утверждёнными игровыми правилами, особенно значение «зачётный RP».
3. Посмотреть SQLite schema, последовательность миграций, фактическую настройку foreign_keys и journal mode без изменения.
4. Описать логический путь: ответ → серверная проверка → начисление RP → преобразование в FP → подтверждение → UI.
5. Выделить место транзакции, корректность коммита, обработку повторов, источники idempotency.
6. Проверить ограничения, уникальные ключи, индексы по реальным частым SELECT/UPDATE.
7. Исследовать explain-планы на независимом тестовом экземпляре; не проводить тяжёлые запросы на production.
8. Проверить фактическую процедуру резервного копирования и независимого восстановления — без запуска несанкционированного backup pilot и без рестарта.
9. Сформулировать только **проверенные** дефекты, уровни риска, предлагаемые тесты и потенциальные миграции.
10. Отдать отдельное ТЗ Codex **только после явного согласования пользователя**, с рамками stage, сроком отката и критериями остановки.

## 4. Контроль счёта на независимой копии

При начислении k≥0 зачётных RP и прежнем остатке r∈[0,9]:
- новые FP = floor((r+k)/10);
- новый остаток = (r+k) mod 10.

Если за одно логическое действие начисление уже подтверждено, повторное обращение не должно изменить значения, при условии однократного действия по фактическим правилам.

Тесты на копии: границы r=0/9, k=0/1/9/10/11, конкурентные повторы одного action_id, сбой между стадиями, таймаут клиента после успешного commit, обработка устаревших версий правил. Это **тестовый план**, не факт, что такой журнал или идентификаторы уже существуют.

## 5. Миграция БД и откат

Прежде чем выбрать SQLite-ограничение по книге с MySQL-примерами, проверить совместимость точного синтаксиса и актуальных версий SQLite. Действие на реальном сервере возможно только по согласованному индивидуальному сценарию, где заранее установлены:
- свежесть независимого восстановления;
- текущее состояние backup timer и точки его безопасной координации;
- предел downtime и критерии здоровья;
- допустимая одна попытка и один контролируемый restart, только если конкретно разрешены;
- немедленная остановка при отклонении;
- срок и процедура отката.

Ни один SQL-скрипт не запускался.

## 3. Подробный тематический разбор для проблемы лагов

### 3.1. Синхронный и асинхронный JavaScript (§9, 12–13, 16, 18–19, 23, 33, 79)

Автор описывает callbacks, Promises, `async/await` и «цикл событий», чтобы разделять отложенное ожидание I/O и непосредственное вычисление. **Полезный проверяемый принцип:** запрос к API можно ожидать без непрерывной синхронной работы JS; но это не говорит, что вся цепочка `fetch → JSON.parse/response.json → обновление DOM → отрисовка` будет короткой.

**Критическая поправка к упрощению источника:** синхронный callback обработчика, большой цикл, декодирование/обработка данных и даже длинная цепь Promise-microtasks могут **задерживать обработку ввода и рендеринг в том же main thread**, несмотря на объявление функции `async`. Отличать **tasks** от **microtasks**, отслеживать моменты обновления кадра и участки CPU. Официальная сверка **вне книги**, не цитата автора: [MDN JavaScript execution model](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Execution_model), [MDN microtask guide](https://developer.mozilla.org/en-US/docs/Web/API/HTML_DOM_API/Microtask_guide).

**Отдельная ошибка §33:** `await` не обеспечивает параллельность *сам по себе*: последовательные `await operationA(); await operationB();` выполняют ожидания последовательно; при независимых операциях можно запускать обе и затем ожидать обе — только если это корректно для логики.

### 3.2. DOM и жизненный цикл обработчиков (§21, 29, 49–50, 54, 56, 58)

В книге разобраны `querySelector`, создание/удаление узлов, события, capturing/target/bubbling и **event delegation**. Практическое знание: для набора динамических элементов иногда можно использовать один обработчик на общем контейнере вместо N индивидуальных слушателей, корректно распознавая цель события.

**Чего не говорит автор:** сколько времени конкретно займёт делегирование и будет ли оно быстрее для данной игры; нельзя массово заменять слушатели без рассмотрения event target, типов событий, propagation и измерения.

**Дополнительная критическая поправка:** книга объясняет регистрацию `addEventListener`, но почти не описывает **снятие обработчика**, управление жизненным циклом через `removeEventListener` или `AbortController.signal`. А именно это важно при повторных переходах между вкладками. Современная специфика подтверждена отдельно [MDN removeEventListener](https://developer.mozilla.org/en-US/docs/Web/API/EventTarget/removeEventListener). Общее число обработчиков может быть симптомом, но не доказанным источником лага.

### 3.3. Замыкания, ссылки, объекты, копирование и Web Storage (§6, 28, 31, 41, 51, 57, 59, 61, 83)

Замыкание сохраняет доступ к внешнему лексическому окружению. Это правильно для организации UI и обработчиков, но **при неподходящем жизненном цикле** замыкание может удерживать связанные объекты/DOM дольше необходимого. Из самой книги **нельзя заключить**, что у игры имеется утечка. Нужен измерительный тренд heap и retains при одинаковых действиях.

Источником описаны `localStorage/sessionStorage`, массивы и `JSON.stringify/parse`, операции spread/`Object.assign` и их **поверхностная** копия. **Для мобильной отзывчивости** потенциально важна стоимость больших сериализаций/клонов на главном потоке, а не только корректность синтаксиса. Отдельно проверять, что Web Storage синхронен и способен создавать паузы; эта особенность напрямую не измерена автором.

### 3.4. Работа с API, HTTP, обработка ошибок (§10, 15, 19)

Автор описывает REST-подобные операции и исключения. **Методическое следствие:** ошибка сети, неуспешный HTTP-status, exception JS и отсутствие кадра готового UI — разные события. Отдельно отслеживать `request begin / response received / UI ready`; не делать вывод, что «плохой API», если ответ пришёл быстро, а обработка затянулась.

Представленный `fetch` пример вызывает `response.json()`, но не всегда отдельно проверяет `response.ok`. В реальном протоколе проверок это разные классы ошибок. **Никаких вмешательств в игровой API не выполнялось.**

### 3.5. Циклы, методы массивов, алгоритмы, функции (§5, 17, 24–25, 35–36, 39–40, 42, 46, 60, 66, 71–75, 80, 89)

На примерах пройдены `sort`, `map`, `filter`, `reduce`, `forEach`, `while`, `for..of`, `flatMap`, объектные методы и структуры данных. Метод `sort` меняет исходный массив (что автор показывает), `map` и `filter` обычно создают новый результат. **Нельзя автоматически объявлять `for` быстрее или `map` медленнее**: для действительно тормозящего игрового callback нужен профиль, конкретные объёмы данных и тест с тем же сценарием.

### 3.6. Мемоизация — §99

Автор показывает кеш результатов функции, где ключ строится через `JSON.stringify(args)`. Это иллюстрирует идею избегания повторных вычислений для чистых функций. **Но алгоритм из книги имеет ограничения:**
- неограниченный `cache = {}` будет расти при уникальных аргументах, удерживая значения, и не очищается;
- сериализация аргументов сама может быть дорогой, а циклические объекты приводят к ошибке;
- JSON не одинаково представляет все JS-значения (например, `undefined`, функции, некоторые числа), поэтому разные аргументы потенциально дадут одинаковый ключ;
- оператор `key in cache` смотрит в цепочку прототипов, а не исключительно в собственные поля кеша; результат может быть неожиданным для произвольных строковых ключей.

**Вывод:** «добавим кеш повсюду» может **ухудшить память и FPS**. Решение о кешировании только после профилирования повторных дорогих вычислений, с определённой стратегией размера/инвалидации. Это критическая оценка, **не эксперимент над игрой**.

### 3.7. React-хуки — §70

Упоминаются `useState`, `useEffect`, `useContext`, `useReducer`, `useCallback`, `useMemo`. **Наличие React в игре не установлено**; список не должен становиться основанием для подключения новых фреймворков. `useMemo/useCallback` не являются универсальным ускорением — нужна версия React и данные конкретного профиля.

## 6. Практическая применимость — ТОЛЬКО гипотезы

[Отдельный исследовательский реестр с критериями опровержения](./Кириченко_052_JavaScript_Гипотезы_Mini_App_DRAFT.md) содержит направления без реализации:
1. очередь задач / микрозадач блокирует отрисовку;
2. при смене вкладок остаются подписки и замыкания;
3. синхронный JSON/Web Storage накладывается на критический пользовательский переход;
4. ненужные DOM операции / вычисления занимают main thread;
5. необоснованная мемоизация и кеширование увеличивают память;
6. ответ API и первый готовый кадр ошибочно смешаны в одной метрике.

**Ничего не проверено на реальной игре.** Истинность любой гипотезы требует инструментального замера в Telegram Android WebView, отдельного разрешения на read-only наблюдение и затем отдельного ТЗ на конкретное изменение.

## 2. Часть 1. Основы React и TypeScript — 8 глав, текст пройден

### Глава 1 — обзор назначения React и TS
Автор объясняет компонентность, одностороннее движение данных, виртуальное описание UI, JSX, типизацию и обширную экосистему. **Критическое уточнение:** виртуальный DOM или компонентная декомпозиция не доказывают автоматически высокий FPS. Работа браузера складывается из выполнения JS, обновления дерева, расчёта стилей/layout, paint, raster и compositing; выигрыши зависят от конкретной реализации.

### Глава 2 — окружение Node, npm, редактор, CRA, TypeScript
Последовательная процедура создания проекта и настройки типов. Материал полезен для понимания того, **что** составляет пользовательский bundle и цепочку сборки, но **не** содержит количественного сравнения bundles/кодсплиттинга/доставки статики.
**Редакционная поправка по состоянию на 2026:** Create React App, предлагаемый как основной стартовый способ, объявлен React **deprecated** для новых приложений (https://react.dev/blog/2025/02/14/sunsetting-create-react-app). Это внешняя официальная проверка, **не часть текста книги**.

### Глава 3 — компонентная структура, запуск, точка входа, README
Обсуждаются функциональные и классовые компоненты, корневой компонент, `createRoot`, StrictMode, `tsconfig.json`, структура проекта, базовая сборка. **Критическая фактическая неточность**: в одном примере автор утверждает, что `reportWebVitals()` «по умолчанию отправляет данные в Google Analytics». Документация CRA говорит, что для передачи данных требуется **явно передать callback**, например обработчик метрик (https://create-react-app.dev/docs/measuring-performance/). **Вывод:** для диагностики нельзя считать, что метрики уже автоматически отправляются куда-либо; телеметрию надо отдельно проектировать, с защитой приватности и разрешением.

### Главы 4 и 5 — JSX, вложенность, композиция, HOC
Описание элементов и JSX, вложенных компонентов, props и переиспользования. Грамотная декомпозиция способна сделать поиск повторных обновлений проще, но не гарантирует снижения работы main thread. Не вводить HOC и другие абстракции только ради предполагаемой оптимизации.

### Глава 6 — props и state
Ключевой механизм: изменение state инициирует новую фазу вычисления React UI, свойства приходят от родителя, data flow обычно сверху вниз. Возможная гипотеза для режима с большим количеством интерактивных элементов — **ненужные обновления слишком широкого поддерева**, но требуется React Profiler/браузерный trace; без подтверждения React в игре эта гипотеза условна.

### Глава 7 — жизненный цикл и очистка
Особенно релевантен пример таймера: создать `setInterval` при монтировании и **очистить** в `componentWillUnmount`. Это защищает от продолжения работы после удаления компонента и полезно как **общий принцип управления ресурсами**. Для функциональных компонентов требуется соответствующее управление эффектами и cleanup (версионно сверять).
**Сценарий для исследовательского протокола:** N последовательных открытий и закрытий вкладки → число активных таймеров/подписок после возврата к исходному состоянию. Проверка не проводилась.

### Глава 8 и дополнительные сведения — props, хуки
Ещё раз разобраны входные свойства, деструктуризация, обзор useState/useEffect/useContext/useReducer и других хуков, включая редакционные терминологические объяснения. Техническая неоднородность источника требует сверять современную рекомендацию отдельно, а не выводить «все хуки одинаково ускоряют код».

## 3. Часть 2. Формы, события, состояние — 4 главы, текст пройден

1. **Обработка событий JSX:** назначение обработчиков, передача аргументов, реакция функциональных компонентов; повторная регистрация обработчиков может повлечь лишнюю работу, но это нужно доказать.
2. **Контролируемые формы:** ввод меняет state, который определяет отображаемое значение; frequent change handlers в тяжёлых деревьях могут быть кандидатом для профиля реакции ввода.
3. **Клиентская/серверная валидация:** клиентская предоставляет feedback, серверная обязательна при проверке авторитетных данных. **Конкретный дефект учебного примера:** общий флаг `isValid` перезаписывается отдельно при проверке поля имени и пароля; результат последнего изменённого поля может маскировать неправильность другого. Нельзя копировать такую логику в игру.
4. **Несколько состояний и обновление компонентов:** надо понимать зависимости между данными и UI; простое множество состояний не само по себе дефект, а аргумент к проверке частоты и критической стоимости обновлений.

**Вывод для Mini App:** измерять, не происходит ли в момент tap/смены вкладки синхронный каскад изменений state и DOM. Без просмотра кода нельзя выбрать нужный метод.

## 4. Часть 3. Данные, API, асинхронность — 4 главы, текст пройден

1. **Работа с API:** `fetch`, преобразование JSON, отправка данных, обработка сетевых ошибок и неуспешных HTTP-ответов. Практическая проблема UI: задержку server response нельзя ошибочно принять за медленный DOM.
2. **Ответ → state → рендер:** в книге представлены разные состояния loading/data/error. Потенциальный источник неверного измерения: «запрос завершён» раньше «экран готов к действию». Это раздельные контрольные точки.
3. **Асинхронность, callbacks, Promises, async/await:** ожидание запроса не всегда блокирует main thread; асинхронность **не гарантирует** отсутствие долгих JS-задач при обработке ответа. Особое внимание следует уделять порядку ответов и запросам предыдущих экранов (race), если будут доказаны.
4. **Redux, MobX, Axios, React Query:** варианты локального/глобального состояния и серверного кеша. Книгу нельзя использовать как мандат на замену стеков или добавление новой библиотеки; изучать только те, что реально присутствуют. Автор переоценивает общее сходство Axios и React Query: Axios — HTTP-клиент, а React Query — управление *server state* и кешем/инвалидацией.

**Критическое замечание о безопасности:** POST **не становится безопасным** только потому, что данные не видны в URL. Необходимы HTTPS, авторизация, секреты вне публичного клиента, защита от утечек и валидация на сервере. Смена HTTP-метода не решает защиту Telegram initData.

## 5. Часть 4. Роутинг и навигация — 3 главы, текст пройден

Автор описывает маршруты, компоненты страниц, параметризованные пути, `useParams`, `useHistory`, охрану маршрутов и array.map/reduce. Самое близкое к повторным лагам при переходах между вкладками — различие между:
- навигацией, когда сохраняется дерево компонентов и изменяется представление;
- размонтированием одних компонент и монтированием других;
- полным перезапуском/загрузкой страницы;
- сменой адреса URL при том же отображении.
**Предостережение:** **не установлено**, что игра использует React Router или URL-роутинг: вкладки могут быть реализованы другим способом.

**Версионная ошибка:** пример с `<Route component={...} exact>` и `useHistory` относится к **старым API React Router**; не переносить в актуальный проект без проверки текущей документации. То, что интерфейс выглядит «многостраничным», ещё не означает multi-page reload.

## 6. Часть 5. TypeScript в React — 4 главы, текст пройден

Типы: `string, number, boolean, null, undefined, never, unknown, any`; объекты, массивы, кортежи, enum; настройка TS, интерфейсы, пользовательские type aliases, generics, optional, модули и namespaces. **Проверенный отрицательный вывод:** наличие TypeScript не ускоряет браузерную отрисовку само по себе — в браузере выполняется JavaScript, полученный после сборки. TypeScript может снижать дефекты интерфейсов данных, облегчать поддержку и построение наблюдаемости, но эффект на latency в миллисекундах не доказан.

**Критическое замечание по примеру `unknown`:** после проверки `typeof value === 'string'` доступ к `length` обычно валиден вследствие narrowing; в книге такой доступ ошибочно обозначен как ошибка. Это повод не копировать комментарии из иллюстративных листингов без TS-проверки.

## 7. Углублённая типизация (первый блок «Часть 6») — 5 глав, текст пройден

Декораторы, типы функций/компонентов, типизация props и state, события/обработчики, generics в хуках и компонентах. Работа с типизированным состоянием полезна для корректности, но авторские примеры не предоставляют measurements и не демонстрируют снижение стоимости обновления UI. Типы React-событий не заменяют изучения реальных touch и viewport events внутри Telegram.

**Редакционные дефекты структуры:** две отдельные «Главы 3», после которых есть «Глава 4», и неверная стыковка нумерации частей. Для библиографического цитирования указывать **заголовок раздела**, а не полагаться исключительно на номер.

## 8. Продвинутые темы (второй блок «Часть 6», по оглавлению соответствует части 7) — 4 главы, текст пройден

- **Context:** избавление от props drilling; потенциальная область лишних массовых обновлений при часто меняющемся Provider, но это требует React Profiler.
- **Redux:** глобальный store, reducers, dispatch; единое состояние облегчает трассировку причин изменения UI, но само по себе не доказывает ускорение.
- **Redux Thunk:** асинхронные actions и зависимости. Потенциальный race при выходе из вкладки и позднем ответе — проверять, лишь если в игре действительно есть такая библиотека.
- **Рефакторинг:** ориентир — читать и поддерживать код без побочных функциональных изменений; производительность должна сравниваться реальными контрольными замерами, а не ощущениями.

## 9. Часть 8. Тестирование и развертывание — 2 главы, текст пройден

1. **Jest/React Testing Library:** тестирование поведения пользователя, а не деталей реализации, события клика и ожидания UI. Это защищает от функциональных регрессий, **не измеряет автоматически FPS или Interaction to Next Paint**.
2. **Webpack/Babel:** объединение ресурсов, транспиляция, настройка сборки. Размер bundle, parse/eval time, кодсплиттинг и загрузка модулей — кандидаты для измерений; простое добавление Webpack не гарантирует снижения latency. Упомянутые CRA-ориентированные инструменты и конфигурации нуждаются в проверке актуальности.

## 10. Часть 9. Практика, заключение, полезные ссылки — текст пройден

Учебные примеры управления состоянием, списками, редьюсерами, условным отображением и обработкой событий. **Критическая обнаруженная ошибка в упражнении:** для списка покупок используется `filter((item,index)=>index!==action.index || undefined)` — условие избыточно и легко неверно понять. Более серьёзный дефект другого упражнения: текст поля ввода показывается **до нажатия** кнопки, хотя задание требует выводить текст **после нажатия**; обработчик кнопки пуст. Это пример **неполного функционального соответствия даже в учебной задаче**. Старые веб-ссылки проверять отдельно.

## 11. Сводное значение для производительности Telegram Mini App

**Нельзя делать по итогам только этой книги:** заменять всю игру на React, менять стейт-менеджер, пересобирать frontend, переписывать вкладки на Router, автоматически включать/отключать звук, массово добавлять memo/хуки. Неизвестен реальный стек и причина задержек.

**Можно вынести в исследовательскую программу, без запуска измерений:** на смартфоне фиксировать медленные и нормальные переходы между режимами; различать UI render time, API wait, восстановление состояния, медиа и очистку ресурсов; исследовать **рост работы** после серии одинаковых переходов; по результатам только затем решать, нужен ли прицельный фикс.

**Ключевая оценка книги:** полный текст — полезное пособие об основных понятиях и архитектуре, **низкая прямая ценность как специализированного руководства по профилированию mobile WebView**. Реальная причина жалоб пользователя книгой не найдена. Не считать архитектурные шаблоны гарантированным ускорением.

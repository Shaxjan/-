# Telegram Mini App: гипотезы и протокол диагностики задержек — DRAFT / NOT TESTED

**Основание:** [начальный фрагмент книги №047 Р. Л. Сайтса](./Сайтс_Software_Dynamics_047_DRAFT.md). Этот документ — **аналитическая адаптация** общей методики измерения → наблюдения → анализа. **Не является инструкцией на изменение production** и не доказывает конкретный дефект. Книга целиком недоступна, а потому план нельзя представлять как полный метод KUTrace или как рекомендации глав 1–30.

## 1. Что следует измерять как самостоятельные пользовательские транзакции

| ID | Действие | Начало, конец и видимая ошибка | Возможный источник задержки — ГИПОТЕЗА |
|---|---|---|---|
| PERF-H01 | Открыть Mini App из Telegram | tap «Открыть» → интерфейс пригоден к действию; отдельно HTML/JS/CSS и bootstrap | доставка ассетов, TLS, auth/API, WebView, сборка JS |
| PERF-H02 | Сменить вкладку после входа | tap вкладки → первый визуальный отклик → полностью отображён и кликабелен экран | JS-main thread, layout/paint, тяжёлое восстановление компонентов |
| PERF-H03 | Войти в зельеварение | tap → первая интерактивность → стабильные кадры во время действия | синхронный JS, таймеры, анимация, декодирование медиа, API |
| PERF-H04 | Повторять переключения между вкладками | 1-й, 5-й, 10-й, 20-й одинаковый цикл с той же последовательностью | накопление DOM, слушателей, таймеров, объектов и декодированных медиа |
| PERF-H05 | Воспроизвести/приглушить звуки | одно и то же игровое действие при равных состояниях медиа | аудиодекодирование и время main thread; **выводы без сравнения запрещены** |
| PERF-H06 | Проверить повторный вход | первое открытие после очистки только тестового профиля → повторное | загрузка/кеш/инициализация, восстановление состояния |
| PERF-H07 | Игровая транзакция с сервером | событие игрока → запрос → ответ API → отрисованный итог | DNS/TLS, очередь, сервер, база, JSON/DOM после получения |

**Оговорка о данных:** ни один ID не означает, что такое действие уже измерено. Не перечислять реальные пути API, структуры БД, метрики или код, пока read-only аттестация не подтвердила их.

## 2. Порядок диагностики без ошибок причинности

1. **Зафиксировать окружение (должно быть подтверждено).** Устройство, ОС и версия Telegram/WebView; исходный URL, хеш JS, версия серверного API при наличии безопасного способа узнать; сеть, заряд, температура/режим питания. **Без чтения токенов и приватных игровых чатов**.
2. **Выбрать один воспроизводимый сценарий**, например смену вкладок или открытие зельеварения, а не оптимизацию «всей игры» сразу.
3. **Собрать базовую серию** одинаковых прогонов: фиксировать время реакции на ввод, число и длительность пропущенных кадров, полный путь запросов и явные long tasks; хранить p50/p95 при достаточной выборке, худший случай отдельно.
4. **Снять диагностическую временную трассу** на *том же* Android именно внутри Telegram; если WebView недоступен через DevTools, обозначить ограничение и собирать только проверяемые внешние показатели. Не создавать Chrome-профили на Windows: ранее они приводили к блокировке локальной учётной записи.
5. **Разметить ожидания и исполнение**, сопоставить хороший и плохой прогон. Не называть медленный request причиной задержки вкладки, если таймлайн показывает, что задержка началась до network request.
6. **Только после подтверждения гипотезы** подготовить отдельное ТЗ для владельца с одним изолированным изменением и возможностью отката. Нет согласования — нет реализации.
7. **Повторить идентичную серию**, сверить распределения, расхождения по устройствам, субъективное ощущение пользователя. Не принимать улучшение одной метрики при ухудшении другой без прозрачного компромисса.

## 3. Какие признаки различают конкурентные причины

| Наблюдение в замере | Возможное объяснение | Что НЕ следует заключать автоматически |
|---|---|---|
| Длинный непрерывный участок JS после tap | тяжёлый обработчик/рендер/сериализация | «сервер виноват» |
| JS почти простаивает, но отрисовка задержана | layout/paint/composite, медиа/GPU, WebView | «надо удалить всю анимацию» |
| Память увеличивается после каждой вкладки | возможное накопление состояния/DOM/объектов | «утечка доказана» без проверки сборщика мусора |
| waterfall ждёт API до показа информации | transport/API/backend; возможно задержка сериализации | «SQLite виновата» |
| воспроизведение замедляется только в Telegram | особенности окружения/Telegram bridge/WebView | «любой браузер всегда медленный» |
| иногда быстрые, иногда очень медленные прогоны | очереди/конкуренция ресурсов, GC, сеть, планировщик | «нужно просто масштабировать сервер» |

## 4. Критерии качества и границы

- **Частота кадров и FPS** описывают одну сторону плавности, **input-to-feedback latency** — другую. Не подменять одну другой. Не изобретать эталон FPS, пока реальные устройства и графическая сложность не изучены.
- **p95/p99** нельзя вычислять как валидный «хвост» на 3–5 прогонах. Для малых выборок показывать все значения и разброс без мнимой статистической точности.
- **Снимать трассы осторожно:** измерительные инструменты сами используют CPU/память; сопоставить записи с трассировкой и без неё, если возможно.
- **Не проводить тяжёлые или рискованные эксперименты на реальных пользователях**, пока не подготовлены безопасные условия. Тестовый бот, отдельный HTTPS-адрес, синтетическая БД и анонимные/обезличенные материалы — отдельные обязательные вопросы при одобрении.
- **Не собирать приватные диалоги, Telegram initData, токены, cookies и прочие пользовательские секреты** в качестве диагностической телеметрии.
- **Проверить источник самой гипотезы:** материал введения Сайтса относится к общим принципам ПО/ОС; конкретные опции Chrome/Android должны быть сверены с современной официальной документацией отдельно, до утверждения ТЗ.

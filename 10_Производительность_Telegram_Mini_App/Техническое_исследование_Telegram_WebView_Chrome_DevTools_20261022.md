## 1. Важное первичное открытие: официальный режим инспекции Telegram Android

Официальная документация Telegram Mini Apps содержит **Debug Mode for Mini Apps**:

1. На **своём тестовом телефоне** включить **USB debugging** в параметрах разработчика Android. Действие выполняет владелец телефона, не ассистент через неизвестный удалённый процесс.
2. В **Telegram Android** открыть **Settings**, пролистать вниз, **дважды выполнить удержание на номере версии Telegram** и в появившихся debug settings включить **Enable WebView Debug**.
3. Подключить Android USB-кабелем к **существующему компьютеру** с Chrome. Открыть в **уже существующем обычном профиле** Chrome `chrome://inspect/#devices`; запустить Mini App на телефоне; при доступности инспекции увидеть WebView как цель и открыть **Inspect**.
4. Получить DevTools **именно этого WebView**, а не самостоятельной вкладки сайта в обычном Chrome. Проверить, что целевой URL и заголовок соответствуют тестовому Mini App, не дублировать неопознанные цели и не запускать автоматически сотни браузерных вкладок.

**Проверено по первоисточнику:** https://core.telegram.org/bots/webapps#debug-mode-for-mini-apps ; инструкция по настройке и возможностям диагностики — https://core.telegram.org/bots/webapps .

**Практические ограничения:** режим отладки зависит от версии Telegram, Android/WebView и наличия доступного USB/компьютера; факт существования инструкции **не подтверждает, что удалённое устройство было реально подключено**. В этой исследовательской сессии **0 подключений iQOO/ADB, 0 реальных WebView-трейсов**. У пользователя ранее была блокировка учётной записи Windows при массовом запуске новых Chrome-профилей, поэтому **не создавать дополнительные профили, не запускать бесконтрольно новые процессы Chrome**. Для исследования достаточно согласованного одиночного сеанса.

### Telegram-специфичный контекст

Telegram описывает **класс производительности устройства** (performance_class в User-Agent, значения `LOW`, `AVERAGE`, `HIGH` в поддерживаемом окружении) и рекомендует учитывать характеристики устройства при выборе визуальных эффектов; сам по себе данный класс **не определяет корень лагов и не заменяет FPS/latency trace**. Следует отдельно фиксировать версии Telegram, Android и WebView, текущий viewport/состояние Mini App, а также условия повторного открытия. Не считать все Android одинаковыми.

Источник: https://core.telegram.org/bots/webapps .

## 2. Единица доказательства — транзакция «действие → видимый отклик»

Нельзя измерять только длительность одной функции или скорость `fetch`, если цель — «плавность игры».

Схема **исследовательских контрольных точек**, а НЕ уже внедрённое инструментирование:

- **T0:** физическое касание/тап по вкладке или кнопке режима.
- **T1:** браузер фактически начинает callback пользовательского события; **входная задержка T0→T1** может быть вызвана другими main-thread tasks.
- **T2:** заканчивается выполнение обработчиков взаимодействия; **обработка T1→T2** включает синхронный JS и связанные callback.
- **T3:** браузер отображает **следующий видимый кадр с изменением**, а не просто запускает `requestAnimationFrame`; **показ кадра T2→T3** включает style/layout/paint/compositor. На записи Performance искать track **Interactions/Frames** и реальную последовательность события.
- **T4:** если нужен результат сетевого вызова, отдельно фиксировать `requestStart`, `responseStart`, `responseEnd`, обработку JSON и **фактическую готовность игрового UI**. Иногда до T3 появится визуальное промежуточное состояние (spinner), но сама логика режима ещё не готова. Их не путать.

В документации web.dev **Interaction to Next Paint** разбит на **input delay, processing duration, presentation delay**. Эта структура помогает разбирать лаги тапов/переключения режима. Однако INP — пользовательская метрика на уровне страницы, а **завершение конкретной игровой операции / готовность данных** может происходить позднее следующего кадра, и его следует измерять отдельно.

Источники:
- https://web.dev/articles/optimize-inp
- https://developer.chrome.com/docs/devtools/performance/reference

## 3. Как получить временные доказательства без вмешательства в код

### Шаг A: Performance → runtime recording

В Inspector WebView открыть **Performance** → нажать **Record**, повторить **ровно один** медленный сценарий (например, переход «главная → зельеварение → назад») → **Stop**. Вторым контрольным прогоном записать **тот же сценарий**, когда пользовательское действие ощущается быстрым, не меняя конфигурацию, источник данных, сборку и подготовку сцены.

Для каждого трейса:
- **Interactions:** определить **input delay / processing / presentation**; убедиться, что пользовательское событие не совпало с другим действием.
- **Main:** осмотреть длинные JavaScript tasks; Call tree / Bottom-up — что заняло время (self vs total duration).
- **Frames:** времена и **dropped / partially presented** frames, а не «FPS на глаз».
- **Rendering / Painting / GPU / raster:** проверять только события, реально присутствующие в данной трассе, поскольку доступность треков зависит от платформы и версии Chrome/DevTools.
- **Screenshots:** помогут сопоставить момент визуального изменения, **если доступны и их запись не слишком влияет на профиль**. Инструментирование само способно менять скорость.
- **Network:** определить, есть ли операция, которая действительно блокирует завершение пользовательского сценария, и что происходило в JS до и после ответа.

**Не делать вывод:** если общий CPU график высокий, это не значит, что именно JavaScript обработчик является причиной. Если кадр пропущен, нужно показать зависимость от конкретной работы main thread/render/raster, а не от присутствия рисунков на экране.

Источник: https://developer.chrome.com/docs/devtools/performance/reference .

### Шаг B: Network → waterfall / Timing

Для запуска или режима с удалёнными данными открыть **Network**, зафиксировать цепочку запросов, провалы TLS, коды ошибок, инициаторов и тайминги:

- **Queueing/Stalled:** очередь или ожидание соединения (зависит от HTTP-поколения и окружения).
- **DNS/Initial connection/SSL:** разрешение имени и транспортное соединение.
- **Waiting (TTFB):** включает **сетевую задержку туда-обратно и время подготовки ответа сервером**; **нельзя приравнивать TTFB к чистому времени backend-обработчика**.
- **Content Download:** передача тела ответа; иногда считывание может задерживать занятый браузер.
- После `responseEnd` отдельно измерить JS JSON/DOM и отображение: это **не часть** серверного ответа.

**Особенно важно** для ранее зафиксированных нестабильных TLS/JS/CSS доставок: «Failed to fetch» может быть как network/transport, так и CORS/другая ошибка; посмотреть статус/тайминг, **не объявлять bootstrap/login единственной причиной без данных**.

Источники:
- https://developer.chrome.com/docs/devtools/network/reference/
- https://developer.chrome.com/docs/devtools/network/overview

**Опасные побочные эффекты:** HAR, Network Payload/Headers, Console и screenshots способны включать URL-параметры, `initData`, cookies и приватные данные. **Никакие сырые отчёты не загружать в публичные GitHub PR.** При тестировании на отдельном тестовом боте с вымышленными данными и разрешённом доступе предварительно вручную убрать секреты. В этом исследовании никаких реальных HAR/секретов нет.

### Шаг C: Memory → сравнение, а не одиночный снимок

Для симптома «чем дольше играю, тем хуже переключаются вкладки»:

1. После стабилизации тестовой сборки сделать **Heap Snapshot A**, зафиксировать состояние и версию среды.
2. **Одинаково** выполнить цикл «открыть конкретный режим → вернуться обратно» некоторое число раз на тестовом состоянии; записать реальные времена каждого повтора.
3. По возможности вернуть приложение **в исходное логическое состояние**, выполнить снимок **Heap Snapshot B**.
4. В **Comparison** найти разницу объектов, **Detached DOM trees**, retained size и цепочки удерживающих ссылок **Retainers**, проверить, остаётся ли память, которая должна освобождаться.
5. Только если видны конкретные ссылки/активные обработчики/объекты и устойчивое накопление после очистки — формулировать гипотезу **утечки**, а не делать вывод по одному росту памяти.

**Очень важные оговорки:**
- Рост heap может быть **нормальным кешем**, а разница между двумя мгновенными снимками — эффектом времени выполнения GC, не утечкой.
- Heap snapshot обычно **запускает GC**; сравнение должно учитывать это поведение.
- Память WebView **не ограничена JS heap**: изображения, декодеры и другие нативные ресурсы могут не попадать в данный список.
- Сама процедура записи снимка/трейса может изменить скорость; недопустимо выполнять её незаметно на чужом устройстве или собирать секреты.

Источники:
- https://developer.chrome.com/docs/devtools/memory-problems
- https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots

## 4. Доказательная развилка: какая подсистема задерживает пользователя?

| Симптом в контролируемой трассе | Что это поддерживает | Что нужно проверить прежде чем называть причину |
|---|---|---|
| Большой интервал **до начала обработчика** | очередь задач / занятый main thread | какая предшествующая задача заняла главный поток; нет ли влияния самого профайлера |
| Callback занимает значительную часть взаимодействия | тяжёлая обработка JS | call stack, сортировки, JSON, синхронные операции и реальные входные данные |
| Callback быстро завершён, следующий кадр долго не показан | style/layout/paint/compositor или иная presentation-задержка | Rendering/Frames треки; последовательность конкретного paint/commit |
| После ответа API до UI проходит много времени | клиентская обработка результата / рендер | отличие responseEnd → application state → frame |
| UI ждёт конкретный запрос, TTFB/соединение велико | транспорт/server/proxy | статус/TLS/DNS, запрет считать TTFB только серверным кодом |
| Время переходов растёт от первого к двадцатому | утечки / кеш / GC / состояние / термальные факторы | парные traces и heap snapshots, температура, фоновая нагрузка |
| Ресурсы отображаются, но кадры пропадают именно при графическом эффекте | возможно canvas/DOM/SVG/raster | определить конкретные вызовы, не сводить всё к «слишком много картинок» |
| В Chrome работает, в Telegram WebView хуже | возможно WebView/bridge/lifecycle / разные версии или кеш | контролировать один билд, телефон, тестовую сеть, версии и режимы; не объявлять Telegram причиной только по различию |
| В обеих средах одинаково плохо, JS/Frames свободны | возможно иной внешний фактор, не графика | полный пользовательский сценарий, работа backend/данных, условия окружения |

Ни один пункт **не доказан для «Мира Поттера»**. Это **карта причинно проверяемых гипотез**, а не журнал найденных багов.

## 5. Минимальный будущий план измерений (без исполнения)

### D0. Разрешение и изоляция

Нужны **отдельное разрешение владельца**, тестовый URL/бот/учётная запись, фиксация точной версии клиента, отсутствие production-токенов, конфиденциальных данных и опасной сетевой нагрузки. Не менять `Shaxjan/potter-quiz`, инстансы API, SQLite, CI или production из этого книжного исследования.

### D1. Проверка канала

В присутствии владельца один раз проверить **Enable WebView Debug** и `chrome://inspect/#devices` на Android. Если нет target: статус **BLOCKED/UNKNOWN**, не подменять доказательство скриншотами из обычного Chrome.

### D2. Базовая воспроизводимость

Сценарий A: старт Mini App → первый доступный экран. **Холодный и тёплый** отдельно. 
Сценарий B: одинаковые переходы **главная ↔ зельеварение** в фиксированном порядке.
Сценарий C: игровой цикл, 10 вопросов, без вымышленных latency/FPS.
Сценарий D: возвращение из фонового Telegram.
Каждому — версии ОС/Telegram/WebView, build SHA, сеть, питание/температура (если доступна), точные действия, измерения каждого повтора, ошибки.

### D3. Контрольные записи

Снять **короткую** Performance запись одного нормального и одного медленного случая для **того же** сценария и окружения. Затем направленно смотреть Network или Memory **только при наличии соответствующего сигнала**. Избегать длительных нагруженных профилей «всё за один раз», которые сами меняют работу приложения.

### D4. Интерпретация и следующий gate

Результат не должен быть вида «посоветовали отключить звук». Корректная исследовательская запись:
- наблюдение: например, задержка между T2 и T3;
- трейс: соответствующая секция main/render/frame/network;
- альтернативные объяснения, которые исключены, и какие ещё **UNKNOWN**;
- точный минимальный участок для **будущей** проверки;
- **NOT TESTED** для любых исправлений до авторизованного отдельного эксперимента.

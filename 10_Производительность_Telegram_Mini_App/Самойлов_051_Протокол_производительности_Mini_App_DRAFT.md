# №051 — исследовательский протокол проверки лагов Telegram Mini App

**DRAFT / NOT TESTED / NOT IMPLEMENTED.** Выведено из критического [исследования справочника Дмитрия Самойлова](./Самойлов_051_Краткий_справочник_тестировщика.md), в сочетании с ранее описанной методикой [№047](./Мини_апп_Методика_диагностики_DRAFT.md). **Это пока НЕ ТЗ на исполнение или тестирование production.**

## 1. Стандарт каждого будущего тест-кейса

| Поле | Что фиксировать |
|---|---|
| ID и операция | Пример `PERF-01`, «открыть вкладку», «запустить игру», «зельеварение» |
| Среда | тестовая сборка с commit/hash, телефон/Android, версия Telegram и Android System WebView, браузерный движок, режим питания, состояние кэша |
| Сеть | Wi-Fi/сотовая, измеренные параметры в пределах возможного, тестовое API/сеть, ошибки запросов |
| Предусловия | холодный старт/повторное открытие, тестовая учётная запись, состояние игры и заполненность данных |
| Действия | точная последовательность с контролем повторов N |
| Ожидаемый результат | экран отображается, взаимодействие доступно, состояние корректно |
| Измерения | время реакции до видимого результата, JS Long Tasks, кадры с пропусками бюджета, память и network timing, если эти каналы доступны |
| Факт | исходные времена каждого повтора, процент ошибок, trace-идентификатор без персональных данных |
| Итог | PASS/FAIL/INCONCLUSIVE с обоснованием; причина **UNKNOWN**, пока не подтверждён критический путь |

**Нельзя** брать одиночную короткую сессию и говорить «лаг устранён». Зафиксировать условие допуска, дисперсию и распределения. Число повторов должно определяться исследовательским дизайном, а не для создания удобного процента ускорения.

## 2. Изолированные сценарии

| ID | Сценарий | Что позволяет разделить |
|---|---|---|
| PERF-01 | Открыть Mini App после закрытия Telegram | доставка HTML/CSS/JS, TLS, bootstrap, рендер первого экрана |
| PERF-02 | Повторное открытие Mini App | загрузка «с нуля» vs кеш/восстановление |
| PERF-03 | 20 однотипных смен вкладки | рост числа активных обработчиков, heap, задержки и ложные повторные запросы |
| PERF-04 | Зельеварение открыть → начать действие → выйти → повторить | стоимость сцены, медиа, анимация, уничтожение ресурсов, API |
| PERF-05 | Игровой цикл 10 вопросов, правильные и ошибочные ответы | реакция ввода, последовательность обработчиков, таймер, запросы |
| PERF-06 | Переключение Telegram в фон и обратно | lifecycle, восстановление состояния, паузы таймеров, сеть |

## 3. Отрицательные проверки

- Ответ API запоздал после выхода из режима: старое состояние не должно портить следующий экран.
- Быстрые повторные касания не должны плодить одновременные запросы или два состояния игры.
- Отказ загрузки CSS/JS/аудиофайла должен быть видимым и иметь контролируемое восстановление, а не бесконечное ожидание.
- Повторные открытия не должны увеличивать активные циклы, listeners и память без функциональной причины; это **гипотеза**, не наблюдённый баг.
- Разные размеры viewport, ориентация и возвращение из фона не должны необъяснимо нарушать пользовательский сценарий.

## 4. Маркеры доказательств

Для каждого медленного случая сопоставить:
1. tap → обработчик события;
2. обработчик → локальное изменение данных;
3. начало/конец API (если есть);
4. главный поток JS, style/layout/paint и frame timeline;
5. момент визуального и интерактивного результата;
6. память/heap после повторного выхода из режима.

В последовательном процессе **длительности суммируются**, в параллельном — нет. Не выводить из общего времени сети процент «вины сервера», если параллельно шла клиентская работа.

## 5. Ограничения и безопасность

- **NOT AUTHORIZED:** не запускать нагрузочный JMeter/автоматизированные UI-прогоны на игровом production, не использовать личные Telegram-аккаунты без разрешения, не модифицировать game repo, не подключать ADB к пользовательскому телефону без согласия и отдельного ТЗ.
- Трейсы, снимки, HAR, логи Android могут содержать `initData`, Cookies, идентификаторы и прочие секреты. Нужны обезличивание, минимальные настройки записи, изолированная учётная запись, ручной контроль публикуемого артефакта.
- Сперва допустимы **только книжная методика и изолированные гипотезы**. При отдельном разрешении владельца — безопасный read-only аудит, а после подтверждения причин — отдельное ТЗ на исправление.
- **Знаний книги недостаточно**, чтобы назвать настоящий root cause лагов. Нужны современная документация Android/Chrome/Telegram и пользовательская трасса.

**Все сценарии PERF-01…09 — NOT TESTED. Любые пороги отклика, FPS, p95 и проценты ускорения неизвестны до реального исследования.**
